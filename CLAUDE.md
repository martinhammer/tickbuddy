# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tickbuddy is a Nextcloud app for daily habit/occurrence tracking (a "one-bit journal"), inspired by the Android app [Tickmate](https://github.com/lordi/tickmate). It targets Nextcloud 33–36 (PHP 8.2+).

## Architecture

Standard Nextcloud app with a PHP backend and Vue 3 frontend. Two Vite entry points (`vite.config.ts`):

1. **Main app** (`src/main.ts` → `App.vue`), mounted into `<div id="tickbuddy">` via `templates/index.php`. Four screens in the navigation, one job each (tick, review, understand, set up), see "Main app screens" below: **Today**, **Journal**, **Analytics**, **Tracks**.
2. **Dashboard widget** (`src/dashboard.ts` → `dashboardApp.ts` → `DashboardWidget.vue`): read-only Nextcloud dashboard widget, see below. Registered by `lib/Dashboard/WeekWidget.php` in `Application::register()`.

**Personal settings** → Tickbuddy is a plain PHP template now (`templates/settings/personal.php`, rendered by `PersonalSettings`, no script): one line and an "Open Tracks" button to `/apps/tickbuddy/#tracks`. Still registered in `appinfo/info.xml` (`<settings>`) so old bookmarks find the link; removing it is a later release.

### Main app screens

- **Routing** (`src/routes.ts`, `parseHash`/`hashFor`, unit-tested): the screen lives in the URL hash, so Back/Forward work without a router. `#today`, `#today/YYYY-MM-DD` (an earlier day; a future or unreal date is today), `#journal` (old `#readonly` links land here), `#analytics/<id>`, `#tracks`, `#tracks/<id>` (that track's sidebar open; an unknown or archived id opens the list). No hash or anything unknown is Today. Moving between days on Today, picking a track in Analytics, and switching from one open sidebar to another **replace** the history entry; opening a sidebar from the list pushes one, and closing it then goes back (`sidebarPushed` in `App.vue`).
- **Toolbar choices** (`src/preferences.ts`): "Show private tracks" (the eye, `PrivateToggle.vue`, on Today and the Journal; Analytics follows it), the Journal layout and Editable days are saved on the server (`/api/preferences`) with **one value for desktop and one for mobile**, chosen by `useIsMobile()` (under 1024px), switching live as the width crosses it. Starting values: Days down / Days down, private off / off, Editable days All / Today. Loaded once per page; a failed save keeps the value for the page and toasts "Could not save the setting".
- **Following the day** (`src/useToday.ts`): Today, the Journal and Tracks keep a reactive `today`, moved on one second after local midnight and checked on focus/visibility, with a quiet reload on a new day or when data is over 5 minutes old (the dashboard widget keeps its own copy of the same code).
- **Editable days** (`src/editableDays.ts`, Tickdroid's `EditableDays.isEditable`; the button and its menu are `EditableDaysMenu.vue`, MDI's `calendar-lock-outline`, `calendar-lock-open-outline` while set to All): a locked day shows read-only values instead of controls (the ✓ in the theme colour or nothing, a counter's number with a muted "0"), a click on them toasts, and its notes are read-only, with no "Add a note". In the Journal a locked day looks exactly like an open one at rest (no lock, no dimming, as in Tickdroid) and keeps that look under the pointer, with focus and on a touchscreen. On both screens the toast reads "This day is locked. Use the Editable days button to change that."
- **Today** (`TodayView.vue`, `TodayRow.vue`): a left-aligned column (660px of rows at most), indented past the navigation toggle as a whole, as the Tracks page is, so rows start under the title; one unboxed row per visible track for one day, a line under each. A row is the name block, then the control (checkbox, or round tertiary − and + buttons round the number, in one fixed-width area per row so checkboxes and numbers line up), nothing between them. Line 1 is the name (cut off first, so the squares always show), the last seven days as squares and the run (`src/runText.ts`, Tickcli's wording, in `--color-text-maxcontrast` for streaks and breaks alike) — squares and run **always show the real today**, whichever day is shown; at phone width it wraps under the name. Line 2 is the note icon on every row, then the day's note or a grey "Add a note" (a plain button styled under `.row`), all three opening the note field; a locked day shows the note read-only with a static icon, and no line without a note. The header holds the eye, the Editable days button (only while the day shown is locked, or on a day just unlocked with it, until another day is shown), the "Today" button, then the day arrows. The title follows how far back the day is (`dayHeading` in `dates.ts`: "Today", "Yesterday", "2 days ago" to "6 days ago", then the date), and a "Today" button sits before the day arrows while another day is shown. The note icon, here and in the Journal, is MDI's `note-text-outline`, not a pencil: the pencil means rename only (the sidebar title, as in Tickdroid). At rest it is lighter than the run text, `--color-text-maxcontrast` mixed 75% with the background (3:1 against it, WCAG's minimum for icons); the text colour under the pointer or with keyboard focus. Loads tracks, the seven days' ticks (plus the shown day's when older), stats and the day's notes.
- **Journal** (`JournalView.vue`, `DaysDownGrid.vue`, `TracksDownGrid.vue`, `JournalCell.vue`): two layouts, Days down (rows of days, newest first) and Tracks down (rows of tracks, days across, today first). The layout button shows MDI's `phone-rotate-landscape` in Days down (the portrait phone is the current layout, the arrow points to the other) and `phone-rotate-portrait` in Tracks down. Both scroll inside one container under a fixed toolbar, with a sticky header row and first column, and load 30 more days as the end comes into view. A cell reads like the old View journal at rest and shows its controls under `:hover`/`:focus-within` in one floating bar with a shadow, vertically centred on the row and placed from the cell's centre (not centred on the cell), so the value never moves: the checkbox where the ✓ sits, then a divider and the note button (Today's size, 32px with a 20px icon); a counter's number where it sits, "−" and "+" about 30px either side, then the divider and note button. The bar may cover neighbouring cells. On `@media (hover: none)` the same arrangement always shows, in the cell rather than floating, without the note button. Controls stay in the DOM so Tab reaches them. A date (or day header) opens Today on that day; a track name opens its Analytics. "Go to date" (an `NcPopover` with `NcDateTimePickerNative`) makes the chosen day the first one. A "Today" button shows whenever today is out of view, after Go to date or after scrolling today's row or column under the sticky header row or name column (measured on scroll against the `data-sticky` corner and the `data-today` row/column, not an `IntersectionObserver`, which can't see what a sticky cell covers), and comes back. Cells talk to the view through `JournalActions` (`src/journal.ts`).
- **Notes** (`NoteField.vue`, `NoteText.vue`): shown with line breaks kept, clamped to three lines with "Show more". Editing in place: Enter saves, Shift+Enter is a new line, Escape cancels, **losing focus saves**; saving it empty (Enter or clicking away) deletes the note. There is no ✕: it read as "close this field". The hint under the field says so. Saving sends `notes/set` (or `DELETE /api/notes` for empty), only when the trimmed text changed. Note text is always rendered escaped (`v-text`/`{{ }}`, never `v-html`).
- **Tracks** (`TracksView.vue` and its dialogs): the only screen that asks for archived tracks (`?includeArchived=true`). Active tracks as `NcListItem`s (drag handle, type line, ⋯ menu: Show analytics, Move up/down, Archive, Delete); the row opens `NcAppSidebar` (`TrackSidebar.vue`: name editable in place, Private switch). Archived tracks go in a collapsed "Archived tracks (n)" list under it, alphabetical, with Restore and Delete: hidden when nothing is archived, collapsed on every load, opened after every successful archive. The delete confirm for an active track offers "Archive instead" (no second confirm), via the dialog's `actions` slot. New track (`NewTrackDialog.vue`) creates with `POST /api/tracks`, then makes it private with a second `PUT` (the server takes no `private` on create; adding it would change the create's `Idempotency-Key` fingerprint). Import and Export are dialogs from the header's ⋯ menu. `TracksView` renders its own `NcAppContent` with the sidebar beside it; the other screens sit in `App.vue`'s.
- **Writes**: yes/no days are written with `POST /api/ticks/set` and the state the control now shows, counters with `POST /api/ticks/increment` and ±1, never `toggle` or an absolute value worked out from what the page loaded, so a click never undoes another client's change. No optimistic updates: the control shows the server's answer.
- **Track types**: wherever code branches on `track.type`, an unknown type must take a read-only branch ("Not supported yet" on Today, the stored value in the Journal), never the counter branch.

### Shared front-end modules

Small, Vue-free TypeScript modules in `src/`, used across the screens and the dashboard widget (the pure ones unit-tested with Vitest, `src/*.test.ts`):
- `types.ts` — `Track`, `Tick`, `Run`, `TrackStats` (one `GET /api/stats` entry), `Note`, `Preferences`, `JournalLayout` and `EditableDays`.
- `dates.ts` — `userLocale`, local `YYYY-MM-DD` helpers (`toDateStr`, `parseDateStr`, `addDays` via `setDate` so DST days stay one day, `todayStr`), `fmtDate` ("Mon 5 Oct 2026"), `fmtDayLabel` ("Mon 19 Oct", with the year outside this one), `dayHeading` (Today's title and the line under it) and `isWeekend`.
- `heatmap.ts` — heatmap shading: `LEVEL_ALPHA`, `levelFor`, `fillFor`, `valueText`, `getPrimaryColor`, `hexToRgba`.
- `api.ts` — `fetchTracks(includeArchived?)`, `fetchTicks(from, to)`, `fetchAllTicks()` (the whole history, `2000-01-01`–`2099-12-31`; only Analytics' charts need it), `fetchStats(today, {trackId?, includeRuns?})`, `fetchNotes`, `setNote`, `deleteNote`, `setYesNo`, `incrementCounter`, `fetchPreferences`, `savePreference`, and `preferStrictHandling()`, which each entry point (`main.ts`, `dashboardApp.ts`) calls once before mounting: an axios interceptor that sends `Prefer: handling=strict` on requests to Tickbuddy's API only (WebDAV reads `Prefer`, so other URLs must not get it).
- `strictHandling.ts` — `PREFER_STRICT`, `isTickbuddyApiUrl`, and `httpStatus(e)` / `errorReason(e)` for reading a failed request defensively, like `ocsError.ts`. `errorReason` is null when the answer has no `reason` (Nextcloud's own errors).
- `routes.ts`, `preferences.ts`, `useToday.ts`, `editableDays.ts`, `runText.ts`, `journal.ts`, `trackMenu.ts` — see "Main app screens" above. `icons.ts` holds the Material Design Icons paths, copied in rather than a dependency.
- `writeErrors.ts` — the shared failure handling for writes. `writeFailed` (ticks and notes, on Today and in the Journal): a `423` with `reason: "archived"` shows "Exercise is archived, so the change wasn't saved." and reloads; a `404` with `reason: "trackNotFound"` reloads too (never a 404 without one: that is Nextcloud's while the app is disabled); any other answer with a `reason` shows the server's message, one without shows "Could not save the change" ("Could not save the note" for notes). `refusedAsReadOnly` (track changes on the Tracks page) reloads and toasts on any 423. Archiving a track already archived elsewhere (423 `archived`) counts as a successful archive.

### Analytics view

`src/components/AnalyticsView.vue` is the **Analytics** screen. It analyses **one track at a time** (picked via `NcSelect`, nothing beside it) and honours the saved "Show private tracks" value (`preferences.ts`), which has no button here: it is set with the eye on Today or in the Journal. The stat cards, streaks and the Streaks/Breaks chart come from `GET /api/stats` (the selected track, `includeRuns=true`); the heatmap, polar and time-series charts still fetch the full tick history over a wide date range and aggregate client-side. Charts use Chart.js via `vue-chartjs`, plus `chartjs-plugin-zoom`.

Contents, top to bottom:
- **Stat cards**: Total, Weekly mean, 2-week trend (a rotated arrow); Current streak/break, Longest streak, Longest break.
- **Calendar heatmap**: a GitHub-contributions-style grid, hand-rolled as SVG (no charting library). Shows a trailing **365 days**, extended further back when the track has older history, in a horizontally scrolling container pinned to today. Weekday labels sit in a **fixed column outside the scroller** so they stay visible; month labels are slanted and scroll with the grid. **Boolean** tracks render one shade; **counter** tracks quantise into four levels against that track's own max, the stats' `maxValue`, so future-dated ticks don't set the scale and the widget shades a day the same way (small ranges map value→level directly). Empty days use `--color-background-dark`. Hover shows a **custom tooltip styled to match the Chart.js default** (the swatch flattens the cell's translucent fill over `--color-main-background` so it matches the cell in either theme).
- **Streaks/Breaks**: a zoom/pan line chart of alternating streak (up) and break (down) run lengths, with a tertiary "Reset zoom" `NcButton`.
- **Days of week** and **Months** polar-area charts, aggregated across all years. Slice shading is **darker = higher value**, reinforcing the slice radius and matching the heatmap's Less→More direction (`polarShades`).
- **Weeks / Months / Quarters / Years** time-series line charts (`buildTimeSeries`; weeks use ISO 8601).

Key conventions:
- **First day of week** comes from `getFirstDay()` (`@nextcloud/l10n`), stored as `localeFirstDay` (0=Sun..6=Sat). This reads Nextcloud's server-injected `window.firstDay`, so it is **consistent across browsers** — do **not** revert to calling `Intl.Locale` week-info directly (Chromium exposes the `weekInfo` property, Firefox only the `getWeekInfo()` method, and they disagree on region-less locales).
- Chart accent colour is read from the `--color-primary-element` CSS variable (`getPrimaryColor`) and tinted via `hexToRgba`, so charts follow the Nextcloud theme.
- **Streak maths lives on the server**, in `StatsService::summariseStreaks` behind `GET /api/stats`, the one implementation every client (web, Tickdroid, Tickcli, TickLLMe) reads, so Analytics and the dashboard widget always agree. The rule: days count from the first tick on or before today, future ticks are ignored, and **an open today never ends a streak** — if today is unticked but yesterday is ticked, the current streak counts up to yesterday (`upToYesterday`, shown as a second tooltip line on "Current streak"); otherwise an open today joins the break.
- Remember sparse storage: a missing day means zero/not-ticked, which the client-side date walks must fill in (they do not assume a row per day).
- **Chart.js option objects need an explicit `ChartOptions<'line'>` (or `<'polarArea'>`) annotation**, as `streaksBreaksData` does. Without one, TS infers `mode: 'x'` as `string` and `min: 'original'` as `string`, which are not assignable to Chart.js's narrow unions, so the `:options` binding fails `npm run typecheck`. The same annotation forces axis `ticks.callback` to accept `number | string` (Chart.js's declared signature) even where a linear scale only ever passes numbers.

### Dashboard widget

`lib/Dashboard/WeekWidget.php` (`IIconWidget`) + `src/components/DashboardWidget.vue`: one row per **non-private** track (always hidden here, whatever the app's eye says) in journal order, the last seven days as heatmap squares (**today first**, on the left), and the current streak or break at the end. Read-only. Loads `GET /api/tracks`, `GET /api/stats?today=…` and the last seven days of `GET /api/ticks` (never the whole history); streaks and counter shading (`maxValue`) come from the stats, so they match Analytics. `today` is reactive state that follows midnight (timer) and tab focus/visibility, with a quiet reload on day change or when data is over 5 minutes old.

Facts about Nextcloud's dashboard that constrain changes:
- **`load()` runs for every registered widget on every dashboard visit**, even when the user hasn't added it. So `src/dashboard.ts` stays tiny: it only registers the `OCA.Dashboard.register` callback and dynamically imports `dashboardApp.ts` when the dashboard calls it. The header icon class lives in the always-loaded `src/dashboard.css`.
- The dashboard host is **Vue 2 on Nextcloud 33/34 and Vue 3 on 35/36**; the widget mounts its own Vue 3 app into the element it is handed, so it works on both. Re-adding a removed widget calls back with a new element; `dashboard.ts` unmounts the old instance.
- The widget gets **288 × 424px** (320px panel minus margins); on the one-column layout (under 710px) the content height is `auto`, so the widget caps itself at 424px and scrolls its rows.
- **Vue widgets get no `IButtonWidget` buttons** (the dashboard only renders them for `IAPIWidgetV2`), so the widget draws its own footer button.
- **The widget id `tickbuddy-week` is permanent**: it is stored in every user's dashboard layout. `WeekWidget::ID` and `WIDGET_ID` in `src/dashboard.ts` must match. A future editable widget gets its own id.

### Backend layers

Follows the Nextcloud AppFramework pattern: **Entity → Mapper → Service → Controller**.

- `lib/Db/` — Entities (`Track`, `Tick`, `Note`, `IdempotencyKey`) and QBMappers. All DB queries live here.
- `lib/Service/` — Business logic. `TrackService` enforces the 99-track limit, type validation, and name trimming. `TickService` handles toggle (boolean), set (counter value or yes/no state) and increment (counter). `StatsService` works out per-track stats and streaks. `NoteService` reads and writes notes and owns the note text rules (`normalise`), which `TickService` and `ImportService` reuse. `StrictHandling` reads `Prefer: handling=strict` (RFC 7240); every write refused on an archived track calls its `refuseArchived($track)`, which throws `ReadOnlyTrackException` (423) for a client that asked and returns for the rest. `ErrorReason` holds the `reason` values of error answers. `IdempotencyService` honours `Idempotency-Key` on the five writes that aren't safe to repeat (see Key design decisions). `ImportService` handles Tickmate and JSON imports. `ExportService` handles JSON export.
- `lib/Controller/` — OCS API controllers. Routes are defined via PHP attributes (`#[ApiRoute]`), not in a routes file.
- `lib/Middleware/` — `PreferenceAppliedMiddleware`, registered in `Application::register()`: adds `Preference-Applied: handling=strict` to every OCS controller response for a request that sent it.
- `lib/Settings/` — `PersonalSection` (sidebar entry with icon) and `PersonalSettings` (renders the settings template).
- `lib/Dashboard/` — `WeekWidget`, the dashboard widget (see above).
- `lib/BackgroundJob/` — `PurgeIdempotencyKeys`, a daily `TimedJob` registered in `appinfo/info.xml` (`<background-jobs>`) that deletes `Idempotency-Key` rows older than `IdempotencyService::KEEP_DAYS` (30).
- `lib/Capabilities.php` — implements `OCP\Capabilities\ICapability`, registered in `Application::register()`. Advertises the app version and a feature-flag map to clients via the core capabilities endpoint (see below). Keep `getCapabilities()` cheap (no DB) — it runs on every capabilities request.
- `lib/Migration/` — Database schema migrations.
- **App metadata**: `appinfo/info.xml` (Nextcloud app manifest — version, dependencies, navigation entry).
- **OpenAPI spec**: `openapi.json` is auto-generated from PHP docblocks on API controllers.

### Data model

Four tables, all scoped per-user:

- **`tickbuddy_tracks`**: id, user_id, name, type (`'boolean'` | `'counter'`), sort_order, private (int 0/1, exposed as bool at the API), archived_at (nullable DATE, mapped as a `YYYY-MM-DD` string; null = active). Max 99 tracks per user, archived ones included.
- **`tickbuddy_ticks`**: id, user_id, track_id, date, value (int, default 1). Unique on (user_id, track_id, date).
- **`tickbuddy_notes`**: id, user_id, track_id, date, text (TEXT; the 500-character limit, `NoteService::MAX_LENGTH`, lives in PHP so it can change without a migration). Unique on (user_id, track_id, date). Its own table, not a column on ticks, because ticks are sparse: unticking deletes the tick row, and a note must outlive that.
- **`tickbuddy_idempotency`**: id, user_id, idem_key (the lower-cased UUID), fingerprint (SHA-256 hex), status (nullable INTEGER; null while the first request runs), response (nullable TEXT, the answer's `ocs.data` as JSON), created_at (BIGINT, Unix seconds). Unique on (user_id, idem_key). Not user data: not exported, imported or deleted with tracks; purged after 30 days.

Key design decisions:
- **Sparse storage**: a tick row existing means "yes" / non-zero count. No row means "no" / zero. Toggling a boolean track inserts or deletes the row. Setting a counter to 0 deletes the row.
- **Track type is immutable**: set at creation, cannot be changed afterward. The API rejects updates to the `type` field.
- **JSON backups match ticks to tracks by `trackIndex`, else by unique name.** Track names may repeat, so `ExportService` adds `trackIndex` (position in the file's `tracks`) to ticks whose track name isn't unique in the file, and only then, so files without duplicates keep the original shape. `ImportService::resolveJsonTicks` resolves every tick to a position *before* the transaction: an invalid `trackIndex`, or a name-only tick matching several tracks, fails the import with nothing written. Tick names are cleaned like track names (trimmed, blank → "Untitled").
- **A Tickmate track is a counter if its "multiple entries per day" setting is on _or_ it has several ticks on one day.** Both checks are needed: older Tickmate backups lack the `multiple_entries_per_day` column, and a track switched off after counting still holds counts that a yes/no import would collapse. Don't simplify it to either check alone: track type is immutable, so a wrong guess can't be corrected after import.
- **Archive.** An archived track (`archived_at` set) keeps its ticks and its `sort_order`, but leaves `GET /api/tracks` unless `includeArchived=true`, and so leaves the journal, Analytics and the dashboard widget without any change to their code. An archived track can only be restored or deleted: every other change (ticks, notes, rename, private, `sortOrder`, re-archiving, a reorder that lists it) is refused with **423 Locked** `{message, reason: "archived"}` for clients that send `Prefer: handling=strict`, and quietly ignored for the rest; the server confirms the header with `Preference-Applied` (no capability flag: an older server just ignores it). Refused whatever the value, so a write that would change nothing gets 423 too. Two compatibility choices here look like bugs and are not — don't "fix" either into an error: (1) **hiding archived tracks by default** is what keeps clients that predate archiving (Tickdroid ≤ 1.2.0) working: the track just disappears for them; (2) **without `Prefer: handling=strict`, writes on an archived track answer 200 (204 for note delete) with the unchanged state** (after the usual 404 and 400 checks), because Tickdroid ≤ 1.3.0's upload queue retries forever on any error but 401 and one stale tick would stall it. This stays until the deprecation switch, when `refuseArchived` throws for every client and the legacy branches go. Restore moves the track to the end of the list (`getMaxSortOrder + 1`) and still applies a name or private sent with it; re-archiving keeps the first date. The archive date is the client's today (`archivedAt`), the server's date only as a fallback. Tick reads (`GET /api/ticks`, `/bounds`) still include archived tracks' ticks; clients match ticks to the tracks they list.
- **Notes outlive ticks, and empty text deletes everywhere.** A note can sit on a day without a tick; unticking (from any client) never touches it, and a note-only day is not a tick in `ticks`, `bounds` or `stats`. Text is stored as sent apart from `\r\n`/`\r` → `\n` and trimming; the server refuses (400, nothing written) rather than alters: not UTF-8, control characters other than `\n`/`\t`, over 500 code points. No HTML stripping or escaping on the way in: whoever displays a note escapes it (the web must use `{{ }}`, never `v-html`). Empty after trimming means "no note" in every write path (`notes/set`, `note` on tick calls, imports, which skip it); appending empty text changes nothing. Archived tracks' notes can't change: 423 for strict clients, the same quiet 200/204 as ticks for the rest. Track delete and both Replace imports delete notes.
- **`note` on `toggle`/`set`/`increment` is optional, and missing ≠ empty.** Missing (null) leaves the day's note alone; sent (even `''`) writes it, and only then does the answer carry `note`. All checks (track, type, value/delta, date, then the note) run before the tick write, then the note is written after it, without a transaction (as for increment). The controllers type `note`/`text` as a scalar union, not `string`: under `strict_types` Nextcloud passes a JSON number through uncast, and a `string` parameter would answer a bare 400 instead of storing the digits.
- **Appending to a note is a compare-and-swap, not a transaction.** `NoteService::appendForTick` reads the note, works out the result (skip if the text's lines already appear as consecutive whole lines, unless duplicates are allowed; 400 if over the limit), then writes it with `NoteMapper::replaceText` (`UPDATE … WHERE id = :id AND text = :old`), or inserts when there is no note. Losing either race (0 rows, or a unique violation) reads again, 3 attempts, then 409. No transaction for the same PostgreSQL reason as increment. The `text` comparison passes `PARAM_STR` explicitly so Oracle compares `to_char(text)`, as a CLOB can't be compared directly. On tick calls, `NoteService::checkAppend` checks the result's length before the tick is written; a 409 (or a note that grew past the limit in between) can only come after it.
- **Idempotency-Key on the writes that aren't safe to repeat, without a transaction.** `POST /api/tracks` (a retry makes two tracks), `toggle` (flips back), `increment` (counts twice), `notes/append` (with `allowDuplicate`, adds twice) and `set` (only unsafe with `appendNote` + `allowDuplicateNote`, but honoured on every `set` to keep the rule simple) take an optional `Idempotency-Key` (draft-ietf-httpapi-idempotency-key-header) holding a UUID, quoted or not (400 `invalidValue` otherwise). Every other write ignores it, as do imports. Each controller method passes its endpoint name and **every parameter in signature order** to `IdempotencyService::run`, which wraps the method's existing body unchanged: claim the key first in its own row (the unique index is the lock), run the body, store its status and data **whatever the status** (a 423 or 409 `noteConflict` replays too), and answer a repeat with the stored answer. A different fingerprint (other parameters, or another endpoint) is 422 `idempotencyKeyReused`; a claim with no answer yet is 409 `requestInProgress`, until it is 5 minutes old (`CLAIM_TIMEOUT_SECONDS`), when it is released (conditional `DELETE … WHERE status IS NULL AND created_at < :t`) and the repeat runs as new: a write may then happen twice, but only after a server failure inside that one request. Failing to store the answer still answers the client. Keys are kept 30 days. No transaction around the key and the write, for the same PostgreSQL reason as increment (a unique violation aborts the whole transaction, and the increment and note writes rely on catching them). The fingerprint is SHA-256 of `serialize()`, not JSON: it keeps `1`/`"1"`/`true`/`null`/`''` apart and can't fail on text that isn't UTF-8 (which a JSON fingerprint would). Changing the fingerprint's recipe answers 422 to in-flight retries for up to 30 days, so don't, without a reason. **Adding a parameter to one of the five changes its fingerprint the same way**: harmless only between releases. A new unsafe write needs a capability flag of its own before it honours the key.
- **Error reasons.** Every error answer of the controllers carries `reason` (an `ErrorReason` constant) next to `message`, typed `TickbuddyError` in `ResponseDefinitions`; a new error answer must get one. Values are API, never renamed. Why: Nextcloud answers some errors itself (a 404 for every app route while the app is disabled, during an upgrade for example), and those carry no `reason`, so clients (Tickdroid's queue) drop a write only on Tickbuddy's own 404 or 400. `InvalidTrackTypeException` maps to `wrongTrackType` in `TickController` but `invalidValue` in `TrackController::create` (an unknown type there).
- **Reorder always renumbers every track.** `TrackService::reorder` builds the full order (`fullOrder()`: listed ids first, then every other track in its previous order) before `TrackMapper::reorder` negates and renumbers, so unlisted tracks (archived ones, or ones another device just created) never keep the negative placeholder and jump to the top.
- **Three tick mutation endpoints**: `POST /api/ticks/toggle` (boolean tracks only), `POST /api/ticks/set` (both: a counter's absolute value, or a yes/no state) and `POST /api/ticks/increment` (counter tracks only). The service layer validates the track type matches the endpoint. All three check `date` is a real `YYYY-MM-DD` date (400, nothing saved). Checks run in the order track (404), type (400), value or delta (400), date (400), note (400), then the archived track's quiet 200, or 423 for strict clients.
- **Increment is atomic without a transaction.** `UPDATE … SET value = value + delta` first (the common case is an existing row); with no row, insert, and on a unique-constraint violation (another request inserted it meanwhile) retry the UPDATE once. A transaction would break that retry on PostgreSQL, where a unique violation aborts the whole transaction. Results of 0 or less delete the row.
- **Stats.** The client sends `today`, because the streak rule depends on whether today is open (server date only as a fallback). Each track ends on its end day `E`: the earliest of `to`, `today` and an archived track's `archivedAt`, so an archived track reads as it stood that day. Future ticks (after `E`) are ignored everywhere. It starts on `S`: `from` when given (every day of the period takes part, so unticked days at its start are a break and a tickless period is one break), else the first tick. Only ticks from `S` to `E` count; runs crossing either edge are cut there, `current`/`upToYesterday` are as of `E`, and `E` before `S` gives the empty answer. The weekly mean runs from `S` to `E`, **counting both end days**, floored at one week, so ticking every day reads exactly 7. `StatsService` reads plain rows (`TickMapper::findValuesByUser`), not entities, and works on day numbers, so a DST change can never make a day 23 or 25 hours.
- **Track names are capped at 255 characters** (`TrackService::MAX_NAME_LENGTH`, the column size), checked in PHP because SQLite doesn't enforce it; imports refuse longer names before writing anything, and the web's name fields carry `maxlength`.
- **`private` is stored as an integer, not a boolean.** The physical column is `INTEGER` on every database (`Types::BOOLEAN` failed to migrate on MySQL), so the `Track` entity must map it with `addType('private', 'integer')`. Binding it as a boolean makes QBMapper emit `'t'`/`'f'`, which Postgres rejects against the integer column. `bool` exists only at the API/JSON boundary — the controller serializes `getPrivate() === 1` and services convert incoming bools with `? 1 : 0`. Golden rule: an entity's `addType()` must always match the physical column type.
- **A migration that has shipped in a tag is immutable.** Correct it with a *new* migration, never by editing it. `Version1001Date20260418000000` created `private` as `Types::BOOLEAN` and was edited to `Types::INTEGER` after v1.0.0 was tagged; because the step is wrapped in `hasColumn('private')`, the edit never reaches a database that already ran the old version — it stays a no-op there forever, and re-enabling the app does not reconcile it (the migration is already recorded as run). No users were affected: v1.0.0/v1.0.1 predate the app store listing (first store release was 1.0.2) and their GitHub assets had zero downloads, so only dev instances installed from source in that window kept the drifted column. Note the asymmetry if this ever recurs: `Types::BOOLEAN` renders as `tinyint(1)` on MySQL, which is harmless for a 0/1 flag, but as a *native* `boolean` on Postgres, where the integer entity reads `'t'`/`'f'` as `0` and integer writes are rejected outright — and converting that column back needs an explicit `USING private::int` cast, not a plain type change.

### API endpoints

**Tracks** (`TrackController`):
- `GET /api/tracks?includeArchived=bool` — list for current user; archived tracks are left out unless `includeArchived=true`
- `POST /api/tracks` — create `{name, type}`; honours `Idempotency-Key` (flag `idempotencyKey`)
- `PUT /api/tracks/{id}` — update `{name?, sortOrder?, private?, archived?, archivedAt?}` (type is rejected). `archived=true` archives on `archivedAt` (`YYYY-MM-DD`, the client's today; server date if missing; 400 if malformed, nothing saved); `archived=false` restores to the end of the list. Other fields are applied first; several in one call are documented as strongly discouraged. On an archived track anything but a restore is 423 for strict clients, else 200 with the unchanged track (checks: 404, `archivedAt` 400, name 400, then 423).
- `PUT /api/tracks/reorder` — reorder tracks `{trackIds[]}`; unlisted tracks follow in their previous order; returns the active tracks only. Listing an archived track changes nothing: 423 for strict clients, else 200 with the current order
- `DELETE /api/tracks/{id}` — delete track and its ticks and notes

Both `{id}` routes declare `requirements: ['id' => '\d+']`. Without it, `{id}` compiles to Symfony's default `[^/]++` and `PUT /api/tracks/{id}` also matches `/api/tracks/reorder` — which route wins then depends purely on method declaration order within the controller (`Router::getAttributeRoutes()` reflects methods in source order, first match wins). The failure is silent: `settype()` casts `"reorder"` to `0`, so a reorder request would 404 as "Track not found". **Any new literal path segment under a route that also has a `{placeholder}` sibling needs the same treatment.**

**Ticks** (`TickController`):
- `GET /api/ticks?from=YYYY-MM-DD&to=YYYY-MM-DD` — fetch ticks in date range
- `GET /api/ticks/bounds` — first/last tick date per track, `[{trackId, oldest, newest}]`. Aggregated in SQL (`MIN`/`MAX` with `GROUP BY track_id`, served by the `(user_id, track_id, date)` unique index) so clients never download whole tick histories just to find where they start. Tracks with no ticks are **omitted** rather than returned with nulls, per the sparse storage convention. Covers all tracks in one response rather than taking a `trackId`: the response is bounded by the 99-track limit, whereas a per-track variant would mean N requests to answer "oldest across all tracks". Private tracks are included — `private` hides tracks in the UI, it is not an authorization boundary, so clients filter it exactly as they do for the tick list.
- `POST /api/ticks/toggle` — toggle boolean tick `{trackId, date}`, answers `{ticked, value: 1|0}`
- `POST /api/ticks/set` — set a tick `{trackId, date, value}`. Counter: `value` is the absolute value (0 deletes), answers `{value: n}`. Yes/no (flag `booleanSet`): `value` is `true`/`false` (also `1`/`0`, `on`/`off`, `yes`/`no`, any case; JSON booleans), answers `{value: 1|0}`; anything else 400. The controller types `value` as a union so Nextcloud doesn't cast `"true"` to 0.
- `POST /api/ticks/increment` — add a signed `delta` (not 0) to a counter tick `{trackId, date, delta}`, atomically; never below 0; answers `{value: n}` (flag `counterIncrement`)
- `GET /api/stats?today=YYYY-MM-DD[&from=YYYY-MM-DD][&to=YYYY-MM-DD][&trackId=n][&includeRuns=bool][&includeArchived=bool]` — per-track `total`, `weeklyMean`, `last7`, `previous7`, `peak7`, `current`, `upToYesterday`, `longestStreak`, `longestBreak`, `firstTick`, `lastTick`, `maxValue`, `minValue` (and `runs` with `includeRuns`). Every track gets an entry, in track list order; always a list, also with `trackId`, which returns an archived track even without `includeArchived` (flag `stats`; `StatsController`). `from`/`to` (flag `statsPeriod`) measure every field within that period, same shape, same code; malformed 400 `From and to must be dates as YYYY-MM-DD`, `from` after `to` 400 `From must be on or before to`
- On an archived track, all three answer 200 with the unchanged state and write nothing, or 423 with `Prefer: handling=strict` (see Archive above).
- All three honour `Idempotency-Key` (flag `idempotencyKey`): a repeat answers as the first request did; 400 `invalidValue` for a key that isn't a UUID, 422 `idempotencyKeyReused`, 409 `requestInProgress`.
- All three take an optional `note` (flag `notes`): missing leaves the day's note, sent replaces it, empty deletes it; the answer then gains `note`, the stored text (`{ticked, value, note}`, `{value, note}`; toggle's `value` is 1 or 0, and its `ticked` stays for Tickdroid 1.3.0 and earlier). Or `appendNote` (flag `notesAppend`), with optional `allowDuplicateNote`, which appends as `notes/append` does; both `note` and `appendNote` is 400 `Send note or appendNote, not both`. All checks, including the appended result's length, run before the tick write; a 409 from the append comes after it.

**Notes** (`NoteController`, flag `notes`):
- `GET /api/notes?from=YYYY-MM-DD&to=YYYY-MM-DD` — `[{trackId, date, text}]` (no id: track and date are the key), date descending, private and archived tracks included. Both dates required and checked (400 `From and to must be dates as YYYY-MM-DD`).
- `POST /api/notes/set` — `{trackId, date, text}`; answers `{text}`, the stored text (`""` when empty text deleted it). Checks: track (404), date (400), text (400). Archived track: unchanged, answers the stored note (423 for strict clients).
- `POST /api/notes/append` — `{trackId, date, text, allowDuplicate?}` (flag `notesAppend`); answers `{text}`, the whole stored note afterwards. No note: stores the text. Otherwise the note, `\n`, the text, unless every line of the text already appears in the note as consecutive whole lines (case-sensitive), when nothing changes (200) unless `allowDuplicate`. Empty text changes nothing (never deletes). Checks: track (404), date (400), text (400, as `set`), result over 500 (400 `The note would be longer than 500 characters`). Lost races are retried 3 times, then 409 `The note changed while appending; try again`. Archived track: unchanged, answers the stored note (423 for strict clients, empty text too). Honours `Idempotency-Key` (flag `idempotencyKey`).
- `DELETE /api/notes?trackId=n&date=YYYY-MM-DD` — 204, also when there was no note; archived track: nothing deleted, still 204 (423 for strict clients).

**Preferences** (`PreferencesController`, only the web calls it, no capability flag):
- `GET /api/preferences` — the web's toolbar choices, six flat fields: `journalLayoutDesktop`/`Mobile` (`daysDown` | `tracksDown`), `showPrivateDesktop`/`Mobile` (bool), `editableDaysDesktop`/`Mobile` (`activeDay` | `activeAndPrevious` | `oneWeek` | `allDays`; the names are Tickdroid's enums in camelCase). Stored as user config `journal_layout_desktop` and so on; a missing or no longer valid value answers its starting value.
- `PUT /api/preferences` — changes only the fields sent; every value is checked first, so one unknown value is 400 `invalidValue` (`Unknown value "x" for editableDaysMobile`) and saves nothing. Answers all six. `defaultView` was removed in 2.4.0 (ignored if sent); the stored `default_view` config is left in place, unread.

**Import/Export** (`ImportController`, `ExportController`):
- `POST /api/import` — import Tickmate `.db` file `{file, mode}`. Disabled Tickmate tracks import archived, with their ticks. Tickmate doesn't record when a track was disabled, so the archive date is its last tick, or the import date (server's) when that is earlier or there are no ticks; disabled tracks count towards the Merge track limit
- `POST /api/import/json` — import Tickbuddy `.json` file `{file, mode}`
- `GET /api/export?includePrivate=bool` — export all data as JSON. Archived tracks are always included and carry `archivedAt` (only they do, so files with nothing archived keep the original format); the JSON import reads it back and fails on a malformed date. A `notes` list (`{track, trackIndex?, date, text}`, matched to tracks like ticks) is written only when there is at least one note, so files without notes keep the original format; a private track's notes go with it. The JSON import checks everything before its transaction opens and fails, changing nothing, on: a track, tick or note that isn't an object, `ticks`/`notes` present but not a list, a tick or note for a track not in the file, a date that isn't real (Tickmate dates too), a tick value its track can't take (yes/no: what `parseYesNo` accepts; counter: a JSON integer ≥ 0), note text the API would refuse, or the same track and day twice. Ticks meaning "nothing" (counter 0, yes/no false) and empty notes are skipped. Its result gains `notes` (0 for Tickmate). Merge's ` (imported)` suffix cuts the name to fit 255 characters.

**Capabilities** (`Capabilities`, not an OCS controller):
- `GET /ocs/v2.php/cloud/capabilities` — core Nextcloud endpoint, not under `/apps/tickbuddy`. Returns `data.capabilities.tickbuddy = {version, apiVersion, features{...}}`. Readable by any authenticated user (app password works). Clients (the mobile app) read this on connect to discover the installed version and which optional API features exist, instead of version-sniffing. `apiVersion` (`Capabilities::API_VERSION`) tracks the client-facing API contract; bump it on a breaking change. `archivedTracks` advertises archive/restore (an older server silently ignores `archived` and answers 200, so clients must check it). `counterIncrement`, `booleanSet`, `stats` and `notes` advertise the endpoints above (an older server answers 400 to `set` on a yes/no track and 404 to the others; it also silently ignores `note` on tick calls, so clients must check `notes` before sending one). `statsPeriod` advertises `from`/`to` on `GET /api/stats`: an older server ignores them and answers all-time stats, so clients must check it first. `notesAppend` advertises `POST /api/notes/append`, `appendNote` on tick calls and the 500-character limit: an older notes build 404s the route and silently ignores `appendNote`. `idempotencyKey` advertises `Idempotency-Key` on the five unsafe writes: an older server ignores the header, so a retried increment counts twice there. `syncDelta`, the remaining "known gap" below, stays `false` — flip it when the endpoint lands. **Any optional endpoint clients may call needs a flag**: additive routes don't bump `apiVersion`, so a flag is the only way a client can tell an endpoint exists rather than discovering it via a 404 (`tickBounds` is the worked example — see `mobile_instructions.md` §1/§3 for the flag + fallback pattern).

### Frontend checks and `@nextcloud/vue` gotchas

`npm run typecheck` is the only check that sees third-party component prop types — ESLint cannot, because no rule reads `@nextcloud/vue`'s type definitions. CI runs it via `.github/workflows/lint-typecheck.yml` (mirrors `lint-eslint.yml`: same pinned action SHAs, same `paths-filter` gate, same summary job for branch protection). **Run it after every `@nextcloud/vue` bump** — that is the class of breakage it exists to catch. It does **not** catch CSS or layout regressions; those need a look at the running app.

Breakages already hit, kept here so they are not reintroduced:

- **`NcButton` colour is `variant`, not `type`.** v9 removed the fallback: `type` is now the native HTML button type (`button`/`submit`/`reset`) and `variant` takes `primary` / `secondary` / `tertiary` / `tertiary-no-background` / …. The same applies to `NcActions` and `NcDialogButton`. `type="primary"` fails silently — the button renders in the default `secondary` variant and emits an invalid HTML `type` attribute.
- **`NcDateTimePickerNative` renders an `NcInputField` since 9.10**, whose root `.input-field` is `width: 100%`. As a flex child it claims the whole row, so the Journal's "Go to date" popover wraps the picker in a fixed-width `.datePicker` div (`JournalView.vue`). Putting a width class on the component itself does not work: `.input-field` is scoped with an attribute selector and outranks a plain class. `@nextcloud/vue` v9 ships no Tooltip directive, so icon buttons carry a native `title` with the same text as their `aria-label`.
- **`NcTextArea` doesn't grow with its text**; `NoteField.vue` sets its height from `scrollHeight` on input. It passes `$attrs` (`maxlength`, `aria-label`, `readonly`) to the `<textarea>`.
- **Nextcloud's core CSS styles every native `<button>` that isn't an `NcButton`** (`core/css/inputs.css`: `button:not(.button-vue, [class^="vs__"])`) as a light primary button: tinted background, padding, 34px min-height, bold, a 3px margin. Its selectors are 0,1,1 (0,2,1 with `:hover`, `:focus`, `:disabled`, and for the margin), so a single CSS-module class loses silently. Plain buttons (grid headers, Journal cells, "Show more") are styled under their component's root class (`.grid .dateButton`, `.cell .noteButton`, `.note .more`), as a scoped style would be, reset `background` on `:hover`/`:focus` too, and take `margin: 0 !important`. `NcButton`s aren't affected; colour their icon (`NcIconSvgWrapper`) rather than the button, whose scoped tertiary colour outranks a class.
- **`NcCheckboxRadioSwitch` draws its state from `modelValue`**, so a refused write needs no putting back (unlike the native `input.checkbox` in Journal cells, which flips itself). To stop a click on it, catch it in the capture phase on a wrapper and `stopPropagation()`: its click handler sits on an inner element, not the input. (Locked days no longer need this: they render no control.)
- **Nextcloud's `input.checkbox + label::before` has an uneven margin** (3px before, 6px after), so a box meant to sit on a centre is off by 1.5px; `JournalCell.vue` zeroes it under `.cell .checkboxSlot`.

## Known gaps / future work

Surfaced while writing the mobile companion app integration guide (`mobile_instructions.md`):

Counter increments merging across devices, once a gap here, are done: `POST /api/ticks/increment` (signed delta, flag `counterIncrement`). Note that a timestamp alone would never have fixed it: two devices pushing the same absolute value are both wrong, so last-write-wins just picks one.

- **No sync delta endpoint.** The API has no `modifiedAt`, ETag, or `since=` parameter. Clients (especially the Android app) must poll full ranges and reconcile locally. If mobile sync UX proves clunky, consider adding a lightweight "changed since X" endpoint. Note this needs **more than a `modified_at` column**: because storage is sparse (untoggling/zeroing deletes the row), a `since=` query over live rows would never surface deletions. A real fix needs tombstones (soft-delete + `deleted_at`) or a separate change log, plus the timestamp/version column. Notes have the same gap (no `modified_at`, deletions are deleted rows), so a delta endpoint must cover them too. Exposed via the `syncDelta` capability flag when it lands.
