# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Tickbuddy is a Nextcloud app for daily habit/occurrence tracking (a "one-bit journal"), inspired by the Android app [Tickmate](https://github.com/lordi/tickmate). It targets Nextcloud 33–36 (PHP 8.2+).

## Architecture

Standard Nextcloud app with a PHP backend and Vue 3 frontend. Two Vite entry points (`vite.config.ts`):

1. **Main app** (`src/main.ts` → `App.vue`), mounted into `<div id="tickbuddy">` via `templates/index.php`. Four screens in the navigation, one job each (tick, review, understand, set up), see "Main app screens" below: **Today**, **Journal**, **Analytics**, **Tracks**.
2. **Dashboard widget** (`src/dashboard.ts` → `dashboardApp.ts` → `DashboardWidget.vue`): read-only Nextcloud dashboard widget, see below. Registered by `lib/Dashboard/WeekWidget.php` in `Application::register()`.

**Personal settings** → Tickbuddy is a plain PHP template now (`templates/settings/personal.php`, rendered by `PersonalSettings`, no script): one line and an "Open Tracks" button to `/apps/tickbuddy/#tracks`. Still registered in `appinfo/info.xml` (`<settings>`) so old bookmarks find the link; removing it is a later release.

### Main app screens

- **Routing** (`src/routes.ts`, `parseHash`/`hashFor`, unit-tested): the screen lives in the URL hash, so Back/Forward work without a router. `#today`, `#today/YYYY-MM-DD` (an earlier day; a future or unreal date is today), `#journal` (old `#readonly` links land here), `#analytics/<id>`, `#tracks`, `#tracks/<id>` (that track's sidebar open; an unknown or archived id opens the list). No hash or anything unknown is Today. Moving between days on Today, picking a track in Analytics, and switching from one open sidebar to another **replace** the history entry; opening a sidebar from the list pushes one, and closing it then goes back (`sidebarPushed` in `App.vue`).
- **Toolbar choices** (`src/preferences.ts`): "Show private tracks" (the eye, `PrivateToggle.vue`, on Today and the Journal; Analytics follows it), the Journal layout and Editable days are saved on the server (`/api/preferences`) with **one value for desktop and one for mobile**, chosen by `useIsMobile()` (under 1024px), switching live as the width crosses it. Starting values: Days down / Days down, private off / off, Editable days All / Today. Loaded once per page; a value changed before the load answers is kept, not overwritten by it; a failed save keeps the value for the page and toasts "Could not save the setting".
- **Following the day** (`src/useToday.ts`): Today, the Journal, Tracks and Analytics keep a reactive `today`, moved on one second after local midnight and checked on focus/visibility, with a quiet reload on a new day or when data is over 5 minutes old (the dashboard widget keeps its own copy of the same code).

In the Journal a locked day looks exactly like an open one at rest (no lock, no dimming, as in Tickdroid) and keeps that look under the pointer, with focus and on a touchscreen. On both screens the toast reads "This day is locked. Use the Editable days button to change that."
- **Today** (`TodayView.vue`, `TodayRow.vue`): a left-aligned column (660px of rows at most), indented past the navigation toggle as a whole, as the Tracks page is, so rows start under the title; under 1024px only the header is, and the rows use the full width with 12px side padding, and the header sticks to the top (`position: sticky`, on the page's background, taking the column's top padding as its own) so the navigation toggle always sits beside the title and the rows scroll under it; one unboxed row per visible track for one day, a line under each. A row is the name block, then the controls, 8px between them. The header holds the eye, the Editable days button (only while the day shown is locked, or on a day just unlocked with it, until another day is shown), the "Today" button, then the day arrows. At rest it is lighter than the run text, `--color-text-maxcontrast` mixed 75% with the background (3:1 against it, WCAG's minimum for icons); the text colour under the pointer or with keyboard focus. One of the two screens that ask for archived tracks (`?includeArchived=true`), with Analytics. - **Writes**: yes/no days are written with `POST /api/ticks/set` and the state the control now shows, counters with `POST /api/ticks/increment` and ±1, never `toggle` or an absolute value worked out from what the page loaded, so a click never undoes another client's change. No optimistic updates: the control shows the server's answer. On Today and in the Journal (`src/cellWrites.ts`) a cell's writes (its tick, or its note) go one at a time, in the order they were made, so its last answer is its value; a load that started before a cell's write leaves that cell as the write left it; and a load replaces only the days it asked for, a cell missing from its answer being removed (sparse), so a reload and a page of older days can arrive in either order.
- **Track types**: wherever code branches on `track.type`, an unknown type must take a read-only branch ("Not supported yet" on Today, the stored value in the Journal), never the counter branch. **Number and Choice**: a day without a tick is `null` in the value maps (`?? null`, never `?? 0`: a Number's 0 is a reading); Yes/No and Counter read null as 0. Both share `NumberField.vue` (a text field: Enter or losing focus saves, Escape restores, empty clears, text that isn't a number or a refused negative stays with a toast, "Enter a valid number") and `ChoiceField.vue` (`NcSelect`, clearable); an empty value shows "…" (U+2026) in both, and on the Journal's Choice button before its drop-down mounts, the field's hidden while it has focus. `NumberField` takes an optional `unit`, which Today passes under 1024px (`useIsMobile`) for a Number with a unit: the field and the unit then share one box (its root `<label>`, which draws the ring, so the focus ring goes round both and a tap on the unit focuses the input; without a unit the label is `display: contents` and the input draws the ring, as the Journal's always does). In the box the input never gets narrower than the value as shown (`--value-chars`, its length or 1 for the "…", times 1ch, plus its 12px of padding) and the unit, uncapped, is cut with "…" only when the box runs out of room; with focus the unit hides and the input has the whole box. `ChoiceField` shows vue-select's ✕ while its list is open too (`.picked` and a global `.vs--open .vs__clear` rule outranking its `v-show`), as the Journal opens the list the moment it mounts and would never show the ✕ otherwise; a press on the ✕ is kept from taking the focus (`keepFocusOnClear`: vue-select keeps it only for presses on the field and the ▾, and the search field losing focus closes the list, and the Journal's bar, before the click that clears), and after clearing an open list is closed (a tick later, as `clearSelection` refocuses the search field), as a pick closes it; with the list closed (Today) focus stays. Both rely on vue-select's class names: recheck after an `@nextcloud/vue` bump. On Today the field and the drop-down share the value column's 140px (see Today above); in the Journal a Number's bar holds the field and the unit, a Choice's a plain button that mounts the `NcSelect` when used (one per grid at most), and the bar stays open while active (`.activeBar`); on a touchscreen both show text and a tap opens the field or list (see Journal above). Days down's headers are at most 120px (96px), Tracks down's day columns fit the widest number on screen (`--day-number-width`, never shrinking, floor 56px/48px; the rule is `.grid.wideDays`, two classes, as the phone rule on `.grid` comes later and would otherwise hold every column at 34px), and a day cell has no `max-width`, so a long number or a touchscreen Counter's "− n +" widens its column rather than being cut or spilling into the next (a Choice's label is still cut at `--cell-label-width`); both draw a unit line under the names only when a track on screen has a unit. Only tracks on screen count, never hidden private ones. Analytics treats them as days with an entry, shading the heatmap with `trackLevel`. Details (`TrackSidebar.vue`) edits a Number's settings and renames a Choice's options in place; New track (`NewTrackDialog.vue`) posts JSON so `options` is a list.

### Shared front-end modules

Small, Vue-free TypeScript modules in `src/`, used across the screens and the dashboard widget (the pure ones unit-tested with Vitest, `src/*.test.ts`):
- `types.ts` — `Track` (with `TrackOption`), `Tick`, `Run`, `TrackStats` (one `GET /api/stats` entry), `Note`, `Preferences`, `JournalLayout` and `EditableDays`.
- `dates.ts` — `userLocale`, local `YYYY-MM-DD` helpers (`toDateStr`, `parseDateStr`, `addDays` via `setDate` so DST days stay one day, `todayStr`), `fmtDate` ("Mon 5 Oct 2026"), `fmtDayLabel` ("Mon 19 Oct", with the year outside this one), `dayHeading` (Today's title and the line under it), `squaresEnd` (the newest of Today's squares), `isWeekend` and `isoWeek` ("2026-W46", counted on UTC calendar days: dividing the time between two local midnights by 24 hours moved every later week one bucket up in years where January is summer time, Sydney's 2021 for one).
- `heatmap.ts` — heatmap shading: `LEVEL_ALPHA`, `levelFor`, `fillFor`, `valueText`, `getPrimaryColor`, `hexToRgba`, and for every type `trackLevel` (a Number between its stats' `minValue` and `maxValue`, an ordered Choice by place, both as `rangeLevel`: lowest level 1, highest 4, all equal 2; a plain list level 2), `trackValueText` ("10.4 km", a label, "No value"), `numberText` and `choiceLabel`. The levels live here so a change after Martin's look is one edit.
- `numberValue.ts` — the web's copy of `NumberValue`: thousandths (`toMilli`, `roundMilli`, half away from zero on integers, since `Math.round` rounds -2.5 to -2), `formatNumber` (rounded on thousandths before `Intl`, which would round the double), `parseNumber` (the locale's decimal separator, its group separator only between groups of three, a point as decimal where grouping isn't one, `-` or `−`; empty is null, anything else `'invalid'`), `toWire` and `sameAsStored`. Numbers follow `userLocale`, as dates do.
- `api.ts` — every read sends `includeAllTypes`; `setValue` (a Number's or Choice's day, `""` to clear), `renameOption`; `fetchTracks(includeArchived?)`, `fetchTicks(from, to, trackId?)` (one track's with a `trackId`, which only Analytics sends), `fetchStats(today, {trackId?, includeRuns?})`, `fetchNotes`, `setNote`, `deleteNote`, `setYesNo`, `incrementCounter`, `fetchPreferences`, `savePreference`, and `preferStrictHandling()`, which each entry point (`main.ts`, `dashboardApp.ts`) calls once before mounting: an axios interceptor that sends `Prefer: handling=strict` on requests to Tickbuddy's API only (WebDAV reads `Prefer`, so other URLs must not get it).
- `strictHandling.ts` — `PREFER_STRICT`, `isTickbuddyApiUrl`, and `httpStatus(e)` / `errorReason(e)` for reading a failed request defensively, like `ocsError.ts`. `errorReason` is null when the answer has no `reason` (Nextcloud's own errors).
- `cellWrites.ts` — `tickKey`, `cellWrites()` (a cell's writes one at a time, and which cells were written since a load started), `keepCells` and `replaceDays`; see "Writes" above.
- `routes.ts`, `preferences.ts`, `useToday.ts`, `editableDays.ts`, `runText.ts`, `journal.ts`, `trackMenu.ts` — see "Main app screens" above. `icons.ts` holds the Material Design Icons paths, copied in rather than a dependency.
- `publicLinks.ts` — the Public links tab's and the Tracks page's words: `linkCountText`, `trackSubname`, `linkDetails`, `lastUsedText` ("Last used yesterday, 22:10"), `revokeText`, `archiveLinksText`, `exampleBase` (an address up to `/ping/`) and `exampleDates`.
- `writeErrors.ts` — the shared failure handling for writes. `writeFailed` (ticks and notes, on Today and in the Journal): a `423` with `reason: "archived"` shows "Exercise is archived, so the change wasn't saved." and reloads; a `404` with `reason: "trackNotFound"` reloads too (never a 404 without one: that is Nextcloud's while the app is disabled); any other answer with a `reason` shows the server's message, one without shows "Could not save the change" ("Could not save the note" for notes). `refusedAsReadOnly` (track changes on the Tracks page) reloads and toasts on any 423. Archiving a track already archived elsewhere (423 `archived`) counts as a successful archive.

### Analytics view

`src/components/AnalyticsView.vue` is the **Analytics** screen. It analyses **one track at a time** (picked via `NcSelect`, nothing beside it; the picker lists active tracks only) and honours the saved "Show private tracks" value (`preferences.ts`), which has no button here: it is set with the eye on Today or in the Journal. The stat cards, streaks and the Streaks/Breaks chart come from `GET /api/stats` (the selected track, `includeRuns=true`); the heatmap, polar and time-series charts read the track's own ticks (`GET /api/ticks` with `trackId`, from the stats' `firstTick` to today, so the stats come first and a track without ticks sends no ticks request) and aggregate client-side, all of them up to the same end day as the stats (`chartsEnd`: today, or an archived track's archive date), so a future-dated tick counts nowhere. The stats are asked for as of `useToday`'s day, so the screen moves on at midnight; that reload and the one on focus after 5 minutes are quiet (the charts stay up, a failure keeps them). A failed load shows an error view with Try again, never the empty-account copy: "Couldn't load your tracks" in place of the screen, or "Couldn't load this track" under the picker; a new track's load clears the previous track's stats first, so its totals can never sit beside another track's charts. Charts use Chart.js via `vue-chartjs`, plus `chartjs-plugin-zoom`.

**A track the picker doesn't list** (archived, or private while private tracks are hidden) is shown when the route names it (`#analytics/<id>`, from a row's ⋯ menu on Tracks): it is the picker's value but not an option. The navigation's link never names one (see `update:trackId` below); a deleted id falls back to the first visible track. An archived one also gets a grey "Archived on 2 March 2026" above the charts, and the heatmap and charts end on the archive date, as its stats do on the server. The view emits `update:trackId` with whether the picker lists the track, so `App.vue`'s `analyticsTrackId` (the navigation's link, "last track viewed") only ever holds a listed one.

Contents, top to bottom:
- **Stat cards**: Total, Weekly mean, 2-week trend (a rotated arrow); Current streak/break, Longest streak, Longest break.
- **Calendar heatmap**: a GitHub-contributions-style grid, hand-rolled as SVG (no charting library). Shows a trailing **365 days**, extended further back when the track has older history, in a horizontally scrolling container pinned to today. Weekday labels sit in a **fixed column outside the scroller** so they stay visible; month labels are slanted and scroll with the grid. **Boolean** tracks render one shade; **counter** tracks quantise into four levels against that track's own max, the stats' `maxValue`, so future-dated ticks don't set the scale and the widget shades a day the same way (small ranges map value→level directly). Empty days use `--color-background-dark`. Hover shows a **custom tooltip styled to match the Chart.js default** (the swatch flattens the cell's translucent fill over `--color-main-background` so it matches the cell in either theme).
- **Streaks/Breaks**: a zoom/pan line chart of alternating streak (up) and break (down) run lengths, with a tertiary "Reset zoom" `NcButton`.
- **Days of week** and **Months** polar-area charts, aggregated across all years. Slice shading is **darker = higher value**, reinforcing the slice radius and matching the heatmap's Less→More direction (`polarShades`).
- **Weeks / Months / Quarters / Years** time-series line charts (`buildTimeSeries`; weeks use ISO 8601).

Key conventions:
- **First day of week** comes from `getFirstDay()` (`@nextcloud/l10n`), stored as `localeFirstDay` (0=Sun..6=Sat). This reads Nextcloud's server-injected `window.firstDay`, so it is **consistent across browsers** — do **not** revert to calling `Intl.Locale` week-info directly (Chromium exposes the `weekInfo` property, Firefox only the `getWeekInfo()` method, and they disagree on region-less locales).
- Chart accent colour is read from the `--color-primary-element` CSS variable (`getPrimaryColor`) and tinted via `hexToRgba`, so charts follow the Nextcloud theme.
- **Streak maths lives on the server**, in `StatsService::summariseStreaks` behind `GET /api/stats`, the one implementation every client (web, Tickdroid, Tickcli, TickLLMe) reads, so Analytics and the dashboard widget always agree. The rule: days count from the first tick on or before today, future ticks are ignored, and **an open today never ends a streak** — if today is unticked but yesterday is ticked, the current streak counts up to yesterday (`upToYesterday`, shown as a second tooltip line on "Current streak"); otherwise an open today joins the break.
- Remember sparse storage: a missing day means zero/not-ticked, which the client-side date walks must fill in (they do not assume a row per day).
- **Chart.js option objects need an explicit `ChartOptions<'line'>` (or `<'polarArea'>`) annotation**, as `streaksBreaksData` does. Without one, TS infers `mode: 'x'` as `string` and `min: 'original'` as `string`, which are not assignable to Chart.js's narrow unions, so the `:options` binding fails `npm run typecheck`. The same annotation forces axis `ticks.callback` to accept `number | string` (Chart.js's declared signature) even where a linear scale only ever passes numbers.

### Dashboard widget

`lib/Dashboard/WeekWidget.php` (`IIconWidget`) + `src/components/DashboardWidget.vue`: one row per **non-private** track (always hidden here, whatever the app's eye says) in journal order, the last seven days as heatmap squares (**today first**, on the left), and the current streak or break at the end. Read-only. Loads `GET /api/tracks`, `GET /api/stats?today=…` and the last seven days of `GET /api/ticks` (never the whole history); streaks and counter shading (`maxValue`) come from the stats, so they match Analytics. `today` is reactive state that follows midnight (timer) and tab focus/visibility, with a quiet reload on day change or when data is over 5 minutes old.

Facts about Nextcloud's dashboard that constrain changes:
- **`load()` runs for every registered widget on every dashboard visit**, even when the user hasn't added it. So `src/dashboard.ts` stays tiny: it only registers the `OCA.Dashboard.register` callback and dynamically imports `dashboardApp.ts` when the dashboard calls it. The header icon class lives in the always-loaded `src/dashboard.css`.
- The dashboard host is **Vue 2 on Nextcloud 33/34 and Vue 3 on 35/36**; the widget mounts its own Vue 3 app into the element it is handed, so it works on both. Re-adding a removed widget calls back with a new element; `dashboard.ts` unmounts the old instance.
- The widget gets **288 × 424px** (320px panel minus margins); on the one-column layout (under 710px) the content height is `auto`, so the widget caps itself at 424px and scrolls its rows.
- **Vue widgets get no `IButtonWidget` buttons** (the dashboard only renders them for `IAPIWidgetV2`), so the widget draws its own footer button.
- **The widget id `tickbuddy-week` is permanent**: it is stored in every user's dashboard layout. `WeekWidget::ID` and `WIDGET_ID` in `src/dashboard.ts` must match. A future editable widget gets its own id.

### Backend layers

Follows the Nextcloud AppFramework pattern: **Entity → Mapper → Service → Controller**.

- `lib/Db/` — Entities (`Track`, `Tick`, `Note`, `IdempotencyKey`) and QBMappers. All DB queries live here.
- `lib/Service/` — Business logic. `TrackService` enforces the 99-track limit, type validation, and name trimming. `TickService` handles toggle (boolean), set (counter value or yes/no state) and increment (counter). `StatsService` works out per-track stats and streaks. `NoteService` reads and writes notes and owns the note text rules (`normalise`), which `TickService` and `ImportService` reuse. `StrictHandling` reads `Prefer: handling=strict` (RFC 7240); every write refused on an archived track calls its `refuseArchived($track)`, which throws `ReadOnlyTrackException` (423) for a client that asked and returns for the rest. `ErrorReason` holds the `reason` values of error answers. `IdempotencyService` honours `Idempotency-Key` on the five writes that aren't safe to repeat (see Key design decisions). `ImportService` handles Tickmate and JSON imports. `ExportService` handles JSON export. `PublicLinkService` manages public links and answers what a call needs (`findByToken`, `isLive`, `touch`, `todayFor`); `EditableDays` is the server's copy of `src/editableDays.ts` (its values, labels and `allows`), also behind `PreferencesController`'s list; `RequestBody` reads a POST's `text/plain` body (at most 64 KiB), which Nextcloud leaves unread.
- `lib/Controller/` — OCS API controllers. Routes are defined via PHP attributes (`#[ApiRoute]`), not in a routes file.
- `lib/Middleware/` — `PreferenceAppliedMiddleware`, registered in `Application::register()`: adds `Preference-Applied: handling=strict` to every OCS controller response for a request that sent it.
- `lib/Settings/` — `PersonalSection` (sidebar entry with icon) and `PersonalSettings` (renders the settings template).
- `lib/Dashboard/` — `WeekWidget`, the dashboard widget (see above).
- `lib/BackgroundJob/` — `PurgeIdempotencyKeys`, a daily `TimedJob` registered in `appinfo/info.xml` (`<background-jobs>`) that deletes `Idempotency-Key` rows older than `IdempotencyService::KEEP_DAYS` (30).
- `lib/Capabilities.php` — implements `OCP\Capabilities\ICapability`, registered in `Application::register()`. Advertises the app version and a feature-flag map to clients via the core capabilities endpoint (see below). Keep `getCapabilities()` cheap (no DB) — it runs on every capabilities request.
- `lib/Migration/` — Database schema migrations.
- **App metadata**: `appinfo/info.xml` (Nextcloud app manifest — version, dependencies, navigation entry).
- **OpenAPI spec**: `openapi.json` is auto-generated from PHP docblocks on API controllers.

### Data model

Six tables, all scoped per-user:

- **`tickbuddy_tracks`**: id, user_id, name, type (`'boolean'` | `'counter'` | `'number'` | `'choice'`), sort_order, private (int 0/1, exposed as bool at the API), archived_at (nullable DATE, mapped as a `YYYY-MM-DD` string; null = active), and four nullable columns, null on every other type: a Number's unit (STRING 255, NULL when empty, as Oracle stores `''` as NULL; answered as `""`), decimal_places (SMALLINT 0–3) and allow_negative (INTEGER 0/1, as private), a Choice's ordered_scale (INTEGER 0/1). Max 99 tracks per user, archived ones included.
- **`tickbuddy_ticks`**: id, user_id, track_id, date, value (int, default 1): a Counter's count, 1 for Yes/No, a **Number's value in whole thousandths** (10.4 is 10400; the column stays INTEGER, so the limit is ±2,147,483.647, `NumberValue::MAX_MILLI`), a Choice's place (1 to n). Unique on (user_id, track_id, date).
- **`tickbuddy_track_options`**: id, user_id, track_id, place (SMALLINT, 1 to 99, the value a day stores), label (STRING 255). Unique on (track_id, place). A Choice's options, fixed once created: only labels change (`PUT /api/tracks/{id}/options/{value}`). Go with their track (delete) and with both Replace imports.
- **`tickbuddy_notes`**: id, user_id, track_id, date, text (TEXT; the 500-character limit, `NoteService::MAX_LENGTH`, lives in PHP so it can change without a migration). Unique on (user_id, track_id, date). Its own table, not a column on ticks, because ticks are sparse: unticking deletes the tick row, and a note must outlive that.
- **`tickbuddy_idempotency`**: id, user_id, idem_key (the lower-cased UUID), fingerprint (SHA-256 hex), status (nullable INTEGER; null while the first request runs), response (nullable TEXT, the answer's `ocs.data` as JSON), created_at (BIGINT, Unix seconds). Unique on (user_id, idem_key). Not user data: not exported, imported or deleted with tracks; purged after 30 days.
- **`tickbuddy_public_links`**: id, user_id (the owner), track_id, token (32 characters of `ISecureRandom::CHAR_HUMAN_READABLE`, unique, kept as it is so the link can be copied again), name, permission (`'tick'` | `'view'`), allowed_days (Editable days' values), last_used_at and revoked_at (nullable BIGINT, Unix seconds). **Revoking keeps the row** (Tickbuddy's only soft delete), so a call to a revoked link can be told from a guess: only a token that never existed counts towards brute-force protection, which would otherwise slow every link called from that server. Rows go with their track (delete), and with both Replace imports; archiving revokes them. Not exported or imported.

Key design decisions:
- **Sparse storage**: a tick row existing means "yes" / non-zero count. No row means "no" / zero. Toggling a boolean track inserts or deletes the row. Setting a counter to 0 deletes the row. **For Yes/No and Counter only**: a Number or Choice stores every value as an entry, a Number's 0 included, and no row means no value (`null` at the API, never 0). `TickService::writeValue` stores any int and deletes on null; the counter path passes `0` as null.
- **Number and Choice.** A Number is stored in thousandths (as Loop does, so a later Loop importer copies values across) and travels as a JSON number holding the stored value exactly (`NumberValue::toWire`: `10.45`, `-1.5`, `72` without `.0`; at most 10 significant digits, so a double holds it). The API answers the stored value, not one rounded to the track's current decimals: fewer decimals only show older days rounded, and switching negative values off keeps past negative days. Every write path (`set`, public links) **rounds to the track's decimal places, half away from zero**, on digit strings (`NumberValue::parse`, never a float; a JSON float is first written back with `json_encode`). This is the one place the server alters rather than refuses, because Decimal places can change later and a script sending two decimals must not start failing. `set` with `value` null or `""` clears a Number or Choice day, and **a `set` without `value` is 400** (the controller asks the request whether it holds `value`; the fingerprint holds `['missing']` then, a list no sent value can be); a public link's `value=` stays 400, so an empty reading can't wipe a day. `toggle` stays Yes/No only, `increment` Counter only. An unknown type in `set` is 400 `wrongTrackType`, never the counter branch. Settings of another type (`unit` on a Choice, `options` on a Number) are 400 on create, update and import. Option labels are trimmed, 1 to 255, and no two the same ignoring case (`mb_strtolower`), unlike track and link names, so a drop-down and a script picking by label can tell them apart. Create writes the track and its options in one transaction inside the end-of-list retry, a new entity each attempt.
- **`includeAllTypes`.** `GET /api/tracks`, `/api/ticks`, `/api/notes`, `/api/stats` and the reorder's answer list only `TrackService::BASE_TYPES` (Yes/No and Counter) unless the client sends `includeAllTypes=true` (read with `Flags`), so a client that predates a type never meets it (Tickcli decision 32, `notes/forward-compat.md`). `trackId` names its track whatever its type, as it names an archived one without `includeArchived`. Bounds, the export, the public link call and every write ignore it. Ticks and notes filter with an id list (`TrackMapper::findIdsByUserAndTypes`), not a join. The web sends it on every read (`api.ts` `ALL_TYPES`, and the reorder in `TracksView.vue`). A new type joins `VALID_TYPES` only, never `BASE_TYPES`, and gets a capability flag.
- **Track type is immutable**: set at creation, cannot be changed afterward. The API rejects updates to the `type` field.
- **JSON backups match ticks to tracks by `trackIndex`, else by unique name.** Track names may repeat, so `ExportService` adds `trackIndex` (position in the file's `tracks`) to ticks whose track name isn't unique in the file, and only then, so files without duplicates keep the original shape. `ImportService::resolveJsonTicks` resolves every tick to a position *before* the transaction: an invalid `trackIndex`, or a name-only tick matching several tracks, fails the import with nothing written. Tick names are cleaned like track names (trimmed, blank → "Untitled").
- **A Tickmate track is a counter if its "multiple entries per day" setting is on _or_ it has several ticks on one day.** Both checks are needed: older Tickmate backups lack the `multiple_entries_per_day` column, and a track switched off after counting still holds counts that a yes/no import would collapse. Don't simplify it to either check alone: track type is immutable, so a wrong guess can't be corrected after import.
- **Archive.** An archived track (`archived_at` set) keeps its ticks and its `sort_order`, but leaves `GET /api/tracks` unless `includeArchived=true`, and so leaves Today, the journal and the dashboard widget without any change to their code (Analytics asks for archived tracks only to show one opened from Tracks). An archived track can only be restored or deleted: every other change (ticks, notes, rename, private, `sortOrder`, re-archiving, a reorder that lists it) is refused with **423 Locked** `{message, reason: "archived"}` for clients that send `Prefer: handling=strict`, and quietly ignored for the rest; the server confirms the header with `Preference-Applied` (no capability flag: an older server just ignores it). Refused whatever the value, so a write that would change nothing gets 423 too. Two compatibility choices here look like bugs and are not — don't "fix" either into an error: (1) **hiding archived tracks by default** is what keeps clients that predate archiving (Tickdroid ≤ 1.2.0) working: the track just disappears for them; (2) **without `Prefer: handling=strict`, writes on an archived track answer 200 (204 for note delete) with the unchanged state** (after the usual 404 and 400 checks), because Tickdroid ≤ 1.3.0's upload queue retries forever on any error but 401 and one stale tick would stall it. This stays until the deprecation switch, when `refuseArchived` throws for every client and the legacy branches go. Restore moves the track to the end of the list (`getMaxSortOrder + 1`) and still applies a name or private sent with it; re-archiving keeps the first date. The archive date is the client's today (`archivedAt`), the server's date only as a fallback. Tick reads (`GET /api/ticks`, `/bounds`) still include archived tracks' ticks; clients match ticks to the tracks they list.
- **Notes outlive ticks, and empty text deletes everywhere.** A note can sit on a day without a tick; unticking (from any client) never touches it, and a note-only day is not a tick in `ticks`, `bounds` or `stats`. Text is stored as sent apart from `\r\n`/`\r` → `\n` and trimming; the server refuses (400, nothing written) rather than alters: not UTF-8, control characters other than `\n`/`\t`, over 500 code points. No HTML stripping or escaping on the way in: whoever displays a note escapes it (the web must use `{{ }}`, never `v-html`). Empty after trimming means "no note" in every write path (`notes/set`, `note` on tick calls, imports, which skip it); appending empty text changes nothing. Archived tracks' notes can't change: 423 for strict clients, the same quiet 200/204 as ticks for the rest. Track delete and both Replace imports delete notes.
- **`note` on `toggle`/`set`/`increment` is optional, and missing ≠ empty.** Missing (null) leaves the day's note alone; sent (even `''`) writes it, and only then does the answer carry `note`. All checks (track, type, value/delta, date, then the note) run before the tick write, then the note is written after it, without a transaction (as for increment). The controllers type `note`/`text` as a scalar union, not `string`: under `strict_types` Nextcloud passes a JSON number through uncast, and a `string` parameter would answer a bare 400 instead of storing the digits.
- **Appending to a note is a compare-and-swap, not a transaction.** `NoteService::appendForTick` reads the note, works out the result (skip if the text's lines already appear as consecutive whole lines, unless duplicates are allowed; 400 if over the limit), then writes it with `NoteMapper::replaceText` (`UPDATE … WHERE id = :id AND text = :old`), or inserts when there is no note. Losing either race (0 rows, or a unique violation) reads again, 3 attempts, then 409. No transaction for the same PostgreSQL reason as increment. The `text` comparison passes `PARAM_STR` explicitly so Oracle compares `to_char(text)`, as a CLOB can't be compared directly. On tick calls, `NoteService::checkAppend` checks the result's length before the tick is written; a 409 (or a note that grew past the limit in between) can only come after it.
- **Idempotency-Key on the writes that aren't safe to repeat, without a transaction.** `POST /api/tracks` (a retry makes two tracks), `toggle` (flips back), `increment` (counts twice), `notes/append` (with `allowDuplicate`, adds twice) and `set` (only unsafe with `appendNote` + `allowDuplicateNote`, but honoured on every `set` to keep the rule simple) take an optional `Idempotency-Key` (draft-ietf-httpapi-idempotency-key-header) holding a UUID, quoted or not (400 `invalidValue` otherwise). Every other write ignores it, as do imports. Each controller method passes its endpoint name and **every parameter in signature order** to `IdempotencyService::run`, which wraps the method's existing body unchanged: claim the key first in its own row (the unique index is the lock), run the body, store its status and data **whatever the status** (a 423 or 409 `noteConflict` replays too), and answer a repeat with the stored answer. A different fingerprint (other parameters, or another endpoint) is 422 `idempotencyKeyReused`; a claim with no answer yet is 409 `requestInProgress`, until it is 5 minutes old (`CLAIM_TIMEOUT_SECONDS`), when it is released (conditional `DELETE … WHERE status IS NULL AND created_at < :t`) and the repeat runs as new: a write may then happen twice, but only after a server failure inside that one request. Failing to store the answer still answers the client. Keys are kept 30 days. No transaction around the key and the write, for the same PostgreSQL reason as increment (a unique violation aborts the whole transaction, and the increment and note writes rely on catching them). The fingerprint is SHA-256 of `serialize()`, not JSON: it keeps `1`/`"1"`/`true`/`null`/`''` apart and can't fail on text that isn't UTF-8 (which a JSON fingerprint would). Changing the fingerprint's recipe answers 422 to in-flight retries for up to 30 days, so don't, without a reason. **Adding a parameter to one of the five changes its fingerprint the same way**: harmless only between releases. A new unsafe write needs a capability flag of its own before it honours the key.
- **The public link call is an OCS route that answers JSON by default.** `PingController` (`GET`/`POST` `/ocs/v2.php/apps/tickbuddy/ping/{token}`, HEAD through GET) is `#[PublicPage]` and `#[NoCSRFRequired]`, so it needs no `OCS-APIRequest`, and overrides `buildResponse` with `$format = 'json'`: OCS's default is XML, which curl (`Accept: */*`) and a browser bookmark would get; `?format=xml` still gives XML. The two `#[ApiRoute]`s on one method need a `postfix`, or they share a name and the second replaces the first. It takes no `$userId`: Nextcloud would inject the caller's session (or null) on a public page; the link's owner is the user. Each call checks the owner exists, is enabled and has Tickbuddy enabled (a public page skips Nextcloud's app check, and a deleted user's data stays), else the same 404 as an unknown token. `#[BruteForceProtection]` throttles only tokens that never existed (`$response->throttle()`), `#[AnonRateLimit(60, 60)]` counts per calling address, all links together. A live link's `last_used_at` is set on every call that reaches it, whatever the answer, at most once a minute (in the `UPDATE`'s condition). The day is today in the owner's time zone (`PublicLinkService::todayFor`: the `core` `timezone` user value, else the server's default; never `IDateTimeZone::getTimeZone($ts, $owner)`, which falls back to the *caller's* session offset), and every day must pass `EditableDays::allows` (never after today) or 403 `dayNotAllowed` with nothing done. Tick calls are `set` (yes/no `true` without `value`; a Number or Choice with `value`, a plain call or `value=` 400 `invalidValue`) or `increment` by 1 (a counter without `value`), with `appendNote` or the `text/plain` body as `appendNote` and never `allowDuplicateNote`, inside `IdempotencyService::run` keyed to the owner (`ping.tick`, `[linkId, value, date, text]`). A Tick link refuses View parameters and the other way round (400), so a script pointed at the wrong link fails at once. `POST /api/public-links` on an archived track is 423 for every client, not only strict ones: no client that predates 423 calls it.
- **Error reasons.** Every error answer of the controllers carries `reason` (an `ErrorReason` constant) next to `message`, typed `TickbuddyError` in `ResponseDefinitions`; a new error answer must get one. Values are API, never renamed. Why: Nextcloud answers some errors itself (a 404 for every app route while the app is disabled, during an upgrade for example), and those carry no `reason`, so clients (Tickdroid's queue) drop a write only on Tickbuddy's own 404 or 400. `InvalidTrackTypeException` maps to `wrongTrackType` in `TickController` but `invalidValue` in `TrackController::create` (an unknown type there). Choice tracks added `optionNotFound` (404, an option rename's unknown place). Public links added `publicLinkNotFound` (404: unknown, revoked, or the owner can't sign in; also an unknown link id), `dayNotAllowed` (403) and `publicLinkLimitReached` (403); the call can't reuse `trackNotFound`, as its caller has no track id and the track may well exist.
- **Reorder always renumbers every track, in one transaction.** `TrackService::reorder` reads the user's tracks locked (`findAllByUser(…, true)`, `FOR UPDATE`), builds the full order (`fullOrder()`: listed ids first, then every other track in its previous order), and `TrackMapper::reorder` renumbers, so unlisted tracks (archived ones, or ones another device just created) never keep a placeholder and jump to the top. The renumbering first shifts every track below both 1 and its lowest value, then numbers them 1..n: MySQL and SQLite check the unique index row by row, so the old single negation (`-(sort_order + 1)`) failed on a mix of positive and negative values, and without a transaction a failure halfway left exactly that mix, which every later reorder then failed on. The shift repairs such an order too. A create or restore elsewhere (`max + 1`, not locked) can still take a number mid-reorder: the unique violation rolls the whole reorder back and it is retried, 3 attempts, then 409 `databaseConflict`. Catching the violation is safe inside this transaction, unlike increment's, because the retry starts a new one.
- **Three tick mutation endpoints**: `POST /api/ticks/toggle` (boolean tracks only), `POST /api/ticks/set` (both: a counter's absolute value, or a yes/no state) and `POST /api/ticks/increment` (counter tracks only). The service layer validates the track type matches the endpoint. All three check `date` is a real `YYYY-MM-DD` date (400, nothing saved). Checks run in the order `allowDuplicateNote` (400), track (404), type (400), value or delta (400), date (400), note (400), then the archived track's quiet 200, or 423 for strict clients. A counter's `value` and `delta` are whole numbers (`TickService::parseWholeNumber`: a JSON integer, or a trimmed string of digits, `delta` with an optional minus; not floats, booleans, `+5`, `5.0` or `5abc`), `value` from 0 (missing or negative is 400, 0 deletes); the limit is `TickService::MAX_VALUE`, 2147483647, the column's range: `set` above it is 400, an `increment` past it is 400 with nothing written (the bound is a condition of the atomic `UPDATE`, which `TickMapper::addToValue` takes as `$max`; a lost insert then reads the row to tell "too large" from "no row"), and a delta below −2147483647 counts as −2147483647, which empties any day.
- **Increment is atomic without a transaction.** `UPDATE … SET value = value + delta` first (the common case is an existing row); with no row, insert, and on a unique-constraint violation (another request inserted it meanwhile) retry the UPDATE; if that row is gone again by then (a decrement to 0, a `set` of 0), insert again, 3 attempts, then the database error (nothing stored: never an answer of 0 for a delta that wasn't applied). A transaction would break that retry on PostgreSQL, where a unique violation aborts the whole transaction. Results of 0 or less delete the row.
- **Losing an insert race is never a 500.** Every insert of a day's tick or note, and every move of a track to the end of the list, catches the unique violation and finishes against the row that won: `toggle` deletes it (two toggles from an unticked day end unticked), yes/no `set` is already as asked, counter `set` and note writes (`writeForTick`) replace its value (last write wins) or insert again if it is already gone, create and restore read the track limit and the end of the list (`getMaxSortOrder + 1`) again. 3 attempts, then the database error escapes, with nothing written. Keep these catches: an exception escaping the controller also leaves an `Idempotency-Key` claim unanswered, so the client's retries get 409 `requestInProgress` for 5 minutes. The 99-track limit is still a count before the insert, so two creates at the same moment can end at 100.
- **Stats.** The client sends `today`, because the streak rule depends on whether today is open (server date only as a fallback). Each track ends on its end day `E`: the earliest of `to`, `today` and an archived track's `archivedAt`, so an archived track reads as it stood that day. Future ticks (after `E`) are ignored everywhere. It starts on `S`: `from` when given (every day of the period takes part, so unticked days at its start are a break and a tickless period is one break), else the first tick. Only ticks from `S` to `E` count; runs crossing either edge are cut there, `current`/`upToYesterday` are as of `E`, and `E` before `S` gives the empty answer. The weekly mean runs from `S` to `E`, **counting both end days**, floored at one week, so ticking every day reads exactly 7. `StatsService` reads plain rows (`TickMapper::findValuesByUser`), not entities, and works on day numbers, so a DST change can never make a day 23 or 25 hours.
- **Track names are capped at 255 characters** (`TrackService::MAX_NAME_LENGTH`, the column size), checked in PHP because SQLite doesn't enforce it; imports refuse longer names before writing anything, and the web's name fields carry `maxlength`.
- **Boolean flags are read with `parseYesNo`, never cast by Nextcloud.** All ten (`includeArchived`, `includeRuns`, `includePrivate`, `includeNotes`, `private`, `archived`, `allowDuplicate`, `allowDuplicateNote`, `showPrivateDesktop`/`Mobile`) take `true`/`false`, `1`/`0`, `on`/`off`, `yes`/`no` in any case, or a JSON boolean; anything else, an empty value included, is 400 `<name> must be true or false`, checked before the track lookup (`Flags`). Typed `bool`, Nextcloud's dispatcher would `settype()` the string, which makes `no` and `off` true. **The docblock is a trap too**: `ControllerMethodReflector` reads `@param bool $x` from the docblock when the signature has no single named type, so the union must be in both (`@param string|int|float|bool|null $x`, which its regex doesn't match). The same goes for `value` and `delta` on the tick calls, whose unions include `float` so a JSON `5.5` reaches the service and gets a `reason` (a strict-types `TypeError` would be the framework's bare 400). **The `Idempotency-Key` fingerprint holds the parsed value** (`Flags::parse`, `parseWholeNumber`), never the raw one, so `delta="1"` and `delta=1`, `"false"` and `false` keep the fingerprints they had when the parameters were typed `int` and `bool`; `IdempotencyServiceTest` pins one hash. The JSON import reads a track's `private` the same way (missing or null is false, anything unreadable fails the import).
- **A NOT NULL column whose entity property starts with a value needs the same `default` in its migration.** `Entity`'s setter ignores a value equal to the one it holds (it isn't marked updated), and `QBMapper::insert` writes only updated fields, so the INSERT leaves the column out and the database refuses the row (MySQL: `1364 Field 'permission' doesn't have a default value`). `tickbuddy_tracks.type` has `'boolean'` for `Track::$type`, `tickbuddy_public_links.permission` `'tick'` and `allowed_days` `'activeAndPrevious'`. The unit tests mock the mappers, so none of them can see a missing default.
- **Stats on Number and Choice count days with an entry**: each stored day counts 1 in `total`, `weeklyMean`, `last7`, `previous7` and `peak7`, and is part of a streak (a Number's 0 and negative values too: `runsFromDays` works on keys). `maxValue`/`minValue` are the highest and lowest stored value over days with an entry (`summarise(…, $countsEntries)`), in the API's form, null without one, and **always null on a plain Choice list** (`orderedScale` off), whose places have no order. Both are `int|float|null` now. The web shades Number squares between them (`heatmap.ts` `trackLevel`).
- **`private` is stored as an integer, not a boolean.** The physical column is `INTEGER` on every database (`Types::BOOLEAN` failed to migrate on MySQL), so the `Track` entity must map it with `addType('private', 'integer')`. Binding it as a boolean makes QBMapper emit `'t'`/`'f'`, which Postgres rejects against the integer column. `bool` exists only at the API/JSON boundary — the controller serializes `getPrivate() === 1` and services convert incoming bools with `? 1 : 0`. Golden rule: an entity's `addType()` must always match the physical column type.
- **A migration that has shipped in a tag is immutable.** Correct it with a *new* migration, never by editing it. `Version1001Date20260418000000` created `private` as `Types::BOOLEAN` and was edited to `Types::INTEGER` after v1.0.0 was tagged; because the step is wrapped in `hasColumn('private')`, the edit never reaches a database that already ran the old version — it stays a no-op there forever, and re-enabling the app does not reconcile it (the migration is already recorded as run). No users were affected: v1.0.0/v1.0.1 predate the app store listing (first store release was 1.0.2) and their GitHub assets had zero downloads, so only dev instances installed from source in that window kept the drifted column. Note the asymmetry if this ever recurs: `Types::BOOLEAN` renders as `tinyint(1)` on MySQL, which is harmless for a 0/1 flag, but as a *native* `boolean` on Postgres, where the integer entity reads `'t'`/`'f'` as `0` and integer writes are rejected outright — and converting that column back needs an explicit `USING private::int` cast, not a plain type change.

### API endpoints

**Tracks** (`TrackController`):
- Every track in every answer gains `publicLinkCount`, its live public links (one `GROUP BY` for a list, 0 on create and for archived tracks), and five settings, null where the type has none: `unit` (`""` when empty), `decimalPlaces`, `allowNegative` (Number), `options` (`[{value, label}]` in place order, one query for a list) and `orderedScale` (Choice)
- `GET /api/tracks?includeArchived=bool&includeAllTypes=bool` — list for current user; archived tracks are left out unless `includeArchived=true`, Number and Choice unless `includeAllTypes=true`
- `POST /api/tracks` — create `{name, type, unit?, decimalPlaces?, allowNegative?, options?, orderedScale?}` (Number: unit, decimal places 0–3 (1 if missing), allowNegative; Choice: `options` required, 2 to 99 labels, as a JSON list or `options[]`); checks name, type, settings of another type, the type's settings, then the limit; honours `Idempotency-Key` (flag `idempotencyKey`), fingerprinting the settings as read (`TrackSettings::fingerprint`)
- `PUT /api/tracks/{id}/options/{value}` — rename one option `{label}` (flag `choiceTracks`); answers the whole track; 404 `trackNotFound`, 400 `wrongTrackType` (not a Choice), 404 `optionNotFound`, 400 label, 423 on an archived track for every client. Digit `requirements` on both placeholders
- `PUT /api/tracks/{id}` — update `{name?, sortOrder?, private?, archived?, archivedAt?, unit?, decimalPlaces?, allowNegative?, orderedScale?}` (type is rejected; `options` is 400, renamed one at a time above). A setting change never changes a stored value; on an archived track it is refused as a rename is. `archived=true` archives on `archivedAt` (`YYYY-MM-DD`, the client's today; server date if missing; 400 if malformed, nothing saved); `archived=false` restores to the end of the list. Other fields are applied first; several in one call are documented as strongly discouraged. On an archived track anything but a restore is 423 for strict clients, else 200 with the unchanged track (checks: 404, `archivedAt` 400, name 400, then 423). A unique violation (a `sortOrder` another track holds) is 409 `databaseConflict` `The tracks changed while saving; try again`, logged; any other database error is a 500.
- `PUT /api/tracks/reorder` — reorder tracks `{trackIds[], includeAllTypes?}`; unlisted tracks follow in their previous order; returns the active tracks only (Yes/No and Counter only without `includeAllTypes`); 409 `databaseConflict` (nothing changed) when other writes kept taking the numbers. Listing an archived track changes nothing: 423 for strict clients, else 200 with the current order
- `DELETE /api/tracks/{id}` — delete track and its ticks, notes and public links

Both `{id}` routes declare `requirements: ['id' => '\d+']`. Without it, `{id}` compiles to Symfony's default `[^/]++` and `PUT /api/tracks/{id}` also matches `/api/tracks/reorder` — which route wins then depends purely on method declaration order within the controller (`Router::getAttributeRoutes()` reflects methods in source order, first match wins). The failure is silent: `settype()` casts `"reorder"` to `0`, so a reorder request would 404 as "Track not found". **Any new literal path segment under a route that also has a `{placeholder}` sibling needs the same treatment.**

**Ticks** (`TickController`):
- `GET /api/ticks?from=YYYY-MM-DD&to=YYYY-MM-DD` — fetch ticks in date range. Both dates required and checked as on notes (400 `From and to must be dates as YYYY-MM-DD`; `from` after `to` 400 `From must be on or before to`; `from` = `to` is one day). `trackId` (flag `trackFilter`) means what it means on stats: missing or 0 is every track, another user's or an unknown id is 404 `trackNotFound` (the range is checked first), an archived track's rows are returned. The answer keeps its shape, entities with `id` (Tickdroid stores it)
- `GET /api/ticks/bounds` — first/last tick date per track, `[{trackId, oldest, newest}]`. Aggregated in SQL (`MIN`/`MAX` with `GROUP BY track_id`, served by the `(user_id, track_id, date)` unique index) so clients never download whole tick histories just to find where they start. Tracks with no ticks are **omitted** rather than returned with nulls, per the sparse storage convention. Covers all tracks in one response rather than taking a `trackId`: the response is bounded by the 99-track limit, whereas a per-track variant would mean N requests to answer "oldest across all tracks". Private tracks are included — `private` hides tracks in the UI, it is not an authorization boundary, so clients filter it exactly as they do for the tick list.
- `POST /api/ticks/toggle` — toggle boolean tick `{trackId, date}`, answers `{ticked, value: 1|0}`
- `POST /api/ticks/set` — set a tick `{trackId, date, value}`. Counter: `value` is the absolute value (0 deletes), answers `{value: n}`. Number: a number (point, no grouping, or a JSON number), rounded to the track's decimals, below 0 400 while `allowNegative` is off, answers the stored value; Choice: a place 1 to n. Both: `null`/`""` clears (answers `{value: null}`), missing is 400. Yes/no (flag `booleanSet`): `value` is `true`/`false` (also `1`/`0`, `on`/`off`, `yes`/`no`, any case; JSON booleans), answers `{value: 1|0}`; anything else 400. The controller types `value` as a union so Nextcloud doesn't cast `"true"` to 0.
- `POST /api/ticks/increment` — add a signed `delta` (not 0) to a counter tick `{trackId, date, delta}`, atomically; never below 0; answers `{value: n}` (flag `counterIncrement`)
- `GET /api/stats?today=YYYY-MM-DD[&from=YYYY-MM-DD][&to=YYYY-MM-DD][&trackId=n][&includeRuns=bool][&includeArchived=bool]` — per-track `total`, `weeklyMean`, `last7`, `previous7`, `peak7`, `current`, `upToYesterday`, `longestStreak`, `longestBreak`, `firstTick`, `lastTick`, `maxValue`, `minValue` (and `runs` with `includeRuns`). Every track gets an entry, in track list order; always a list, also with `trackId`, which returns an archived track even without `includeArchived` (flag `stats`; `StatsController`). `from`/`to` (flag `statsPeriod`) measure every field within that period, same shape, same code; malformed 400 `From and to must be dates as YYYY-MM-DD`, `from` after `to` 400 `From must be on or before to`
- On an archived track, all three answer 200 with the unchanged state and write nothing, or 423 with `Prefer: handling=strict` (see Archive above).
- All three honour `Idempotency-Key` (flag `idempotencyKey`): a repeat answers as the first request did; 400 `invalidValue` for a key that isn't a UUID, 422 `idempotencyKeyReused`, 409 `requestInProgress`.
- All three take an optional `note` (flag `notes`): missing leaves the day's note, sent replaces it, empty deletes it; the answer then gains `note`, the stored text (`{ticked, value, note}`, `{value, note}`; toggle's `value` is 1 or 0, and its `ticked` stays for Tickdroid 1.3.0 and earlier). Or `appendNote` (flag `notesAppend`), with optional `allowDuplicateNote`, which appends as `notes/append` does; both `note` and `appendNote` is 400 `Send note or appendNote, not both`. All checks, including the appended result's length, run before the tick write; a 409 from the append comes after it.

**Notes** (`NoteController`, flag `notes`):
- `GET /api/notes?from=YYYY-MM-DD&to=YYYY-MM-DD` — `[{trackId, date, text}]` (no id: track and date are the key), date descending, private and archived tracks included. Both dates required and checked (400 `From and to must be dates as YYYY-MM-DD`; `from` after `to` 400 `From must be on or before to`). Takes `trackId` as `GET /api/ticks` does (flag `trackFilter`).
- `GET /api/notes/bounds` — first/last note date per track, `[{trackId, oldest, newest}]` (flag `notesBounds`), the notes table's copy of `GET /api/ticks/bounds`: aggregated in SQL, tracks without notes omitted, private and archived included. Independent of ticks: a note-only day counts here and not there.
- `POST /api/notes/set` — `{trackId, date, text}`; answers `{text}`, the stored text (`""` when empty text deleted it). Checks: track (404), date (400), text (400). Archived track: unchanged, answers the stored note (423 for strict clients).
- `POST /api/notes/append` — `{trackId, date, text, allowDuplicate?}` (flag `notesAppend`); answers `{text}`, the whole stored note afterwards. No note: stores the text. Otherwise the note, `\n`, the text, unless every line of the text already appears in the note as consecutive whole lines (case-sensitive), when nothing changes (200) unless `allowDuplicate`. Empty text changes nothing (never deletes). Checks: track (404), date (400), text (400, as `set`), result over 500 (400 `The note would be longer than 500 characters`). Lost races are retried 3 times, then 409 `The note changed while appending; try again`. Archived track: unchanged, answers the stored note (423 for strict clients, empty text too). Honours `Idempotency-Key` (flag `idempotencyKey`).
- `DELETE /api/notes?trackId=n&date=YYYY-MM-DD` — 204, also when there was no note; archived track: nothing deleted, still 204 (423 for strict clients).

**Public links** (`PublicLinkController`, flag `publicLinks`; a link is `{id, trackId, name, permission, allowedDays, url, lastUsedAt}`, `lastUsedAt` Unix seconds or null, the token only inside `url`, built with `IURLGenerator::linkToOCSRouteAbsolute('tickbuddy.ping.call', …)`):
- `GET /api/public-links?trackId=n` — live links, oldest first; `trackId` missing or 0 is every track's; 404 `trackNotFound`. Revoked links are never listed.
- `POST /api/public-links` — `{trackId, name, permission, allowedDays}`, all required; 201. Checks: track 404, archived 423 (every client), name 400 (trimmed, 1 to 255, may repeat), `permission` and `allowedDays` 400 `Unknown value "x" for …`, the 99-per-track limit 403 `publicLinkLimitReached` (a count before the insert, as tracks'). A clashing token makes a new one, 3 attempts. Honours `Idempotency-Key` (`publicLinks.create`).
- `PUT /api/public-links/{id}` — `{name}` only; 404 `publicLinkNotFound` for another user's or a revoked link.
- `DELETE /api/public-links/{id}` — revoke (sets `revoked_at`); 204, also when already revoked.
- **The call**, `GET`/`POST`/`HEAD` `/ocs/v2.php/apps/tickbuddy/ping/{token}` (`PingController`, see Key design decisions): Tick only takes `value`, `date`, `appendNote` or a `text/plain` POST body (both: 400 `Send appendNote or a text body, not both`) and answers `{value, note?}`; View only takes `date`, or `from` and `to` (checked as on `GET /api/ticks`; with `date` 400), and `includeNotes`, and answers `{ticks, notes?}` in `GET /api/ticks`'s and `GET /api/notes`'s shapes. 404 `publicLinkNotFound`, 403 `dayNotAllowed` (`This link's allowed days (+1 day) don't include 2026-11-10`), 400 `wrongTrackType` for a Tick link on a type that isn't yes/no or counter. No 423: archiving revokes the links.

**Preferences** (`PreferencesController`, only the web calls it, no capability flag):
- `GET /api/preferences` — the web's toolbar choices, six flat fields: `journalLayoutDesktop`/`Mobile` (`daysDown` | `tracksDown`), `showPrivateDesktop`/`Mobile` (bool), `editableDaysDesktop`/`Mobile` (`activeDay` | `activeAndPrevious` | `oneWeek` | `allDays`; the names are Tickdroid's enums in camelCase). Stored as user config `journal_layout_desktop` and so on; a missing or no longer valid value answers its starting value.
- `PUT /api/preferences` — changes only the fields sent; every value is checked first, so one unknown value is 400 `invalidValue` (`Unknown value "x" for editableDaysMobile`) and saves nothing. Answers all six. `defaultView` was removed in 2.4.0 (ignored if sent); the stored `default_view` config is left in place, unread.

**Import/Export** (`ImportController`, `ExportController`):
- `POST /api/import` — import Tickmate `.db` file `{file, mode}`. The file is the user's upload, so read as hostile (`readTickmateFile`, after https://www.sqlite.org/security.html): read-only, `trusted_schema = OFF`, SQLite errors as exceptions and so a 400 (`Not a valid Tickmate backup: the file could not be read`), never a 500. Before any row is read, `tracks` and `ticks` must be plain tables of stored columns (`PRAGMA table_xinfo`, `hidden` 0; no `CREATE VIRTUAL`): a virtual generated column is worked out on every read, so a few kilobytes can hold `zeroblob(1000000000)` and make SQLite allocate it outside PHP's `memory_limit`, and `substr()` or `CAST` don't help (they expand it all the same, measured). With those refused, everything read is the file's own bytes, bounded by the 20 MB upload; numbers are still read with `CAST` and names with `substr` to 256 characters, so a long value never reaches PHP, and more than 200,000 ticks (`MAX_TICKMATE_TICKS`, ~700 bytes of PHP memory each while read) is refused after a `count(*)`. Disabled Tickmate tracks import archived, with their ticks. Tickmate doesn't record when a track was disabled, so the archive date is its last tick, or the import date (server's) when that is earlier or there are no ticks; disabled tracks count towards the Merge track limit
- `POST /api/import/json` — import Tickbuddy `.json` file `{file, mode}`. Both imports take `#[UserRateLimit]`, 10 per 10 minutes per route (`ImportController::RATE_LIMIT`); Nextcloud answers 429 itself with an empty `text/html` body (not OCS JSON), so the web's Import dialog goes by the status, with its own toast. On both imports a failure inside the write transaction that isn't the import's own `ImportException` (the track limit) is logged and answered 400 `importFailed` `The import failed, so nothing was imported`; the driver's text never reaches the client
- `GET /api/export?includePrivate=bool` — export all data as JSON. Archived tracks are always included and carry `archivedAt` (only they do, so files with nothing archived keep the original format); the JSON import reads it back and fails on a malformed date. A `notes` list (`{track, trackIndex?, date, text}`, matched to tracks like ticks) is written only when there is at least one note, so files without notes keep the original format; a private track's notes go with it. The JSON import checks everything before its transaction opens and fails, changing nothing, on: a track, tick or note that isn't an object, `ticks`/`notes` present but not a list, a tick or note for a track not in the file, a date that isn't real (Tickmate dates too), a tick value its track can't take (yes/no: what `parseYesNo` accepts; counter: a JSON integer ≥ 0), note text the API would refuse, or the same track and day twice. Ticks meaning "nothing" (counter 0, yes/no false) and empty notes are skipped; a Number's 0 is a reading and kept. Number and Choice tracks carry their settings only on their type (`unit` `""` when empty, `options` as plain labels), a Number's ticks the stored value exactly; the import takes a Number's past values as stored (up to 3 decimals, negatives whatever `allowNegative` says) and fails on settings of another type, a bad option list, a Number value that isn't a JSON number within the limit, or a Choice place the track doesn't have. The export's `version` stays 1. Its result gains `notes` (0 for Tickmate). Merge's ` (imported)` suffix cuts the name to fit 255 characters.

`GET /api/ticks`, `GET /api/notes` and `GET /api/stats` take `includeAllTypes` (see Key design decisions); a tick's `value` is written by its track's type (`NumberValue::forWire`).

**Capabilities** (`Capabilities`, not an OCS controller):
- `GET /ocs/v2.php/cloud/capabilities` — core Nextcloud endpoint, not under `/apps/tickbuddy`. Returns `data.capabilities.tickbuddy = {version, apiVersion, features{...}}`. Readable by any authenticated user (app password works). Clients (the mobile app) read this on connect to discover the installed version and which optional API features exist, instead of version-sniffing. `apiVersion` (`Capabilities::API_VERSION`) tracks the client-facing API contract; bump it on a breaking change. `archivedTracks` advertises archive/restore (an older server silently ignores `archived` and answers 200, so clients must check it). `counterIncrement`, `booleanSet`, `stats` and `notes` advertise the endpoints above (an older server answers 400 to `set` on a yes/no track and 404 to the others; it also silently ignores `note` on tick calls, so clients must check `notes` before sending one). `statsPeriod` advertises `from`/`to` on `GET /api/stats`: an older server ignores them and answers all-time stats, so clients must check it first. `notesAppend` advertises `POST /api/notes/append`, `appendNote` on tick calls and the 500-character limit: an older notes build 404s the route and silently ignores `appendNote`. `idempotencyKey` advertises `Idempotency-Key` on the five unsafe writes: an older server ignores the header, so a retried increment counts twice there. `trackFilter` advertises `trackId` on `GET /api/ticks` and `GET /api/notes`: an older server ignores it and answers every track, so a client filters by `trackId` itself unless the flag is set. `notesBounds` advertises `GET /api/notes/bounds`, which an older server 404s. `publicLinks` advertises `/api/public-links`, `publicLinkCount` on tracks and the call; an older server 404s the routes. `numberTracks` and `choiceTracks` advertise the two types, their fields, `set` on them, `includeAllTypes` on the reads and (Choice) the option rename; `includeAllTypes` has no flag of its own (an older server ignores it and has only the two old types). `syncDelta`, the remaining "known gap" below, stays `false` — flip it when the endpoint lands. **Any optional endpoint clients may call needs a flag**: additive routes don't bump `apiVersion`, so a flag is the only way a client can tell an endpoint exists rather than discovering it via a 404 (`tickBounds` is the worked example — see `mobile_instructions.md` §1/§3 for the flag + fallback pattern).

## Key Conventions

- PHP namespace: `OCA\Tickbuddy\`
- App ID constant: `Application::APP_ID` (`'tickbuddy'`)
- All PHP files use `declare(strict_types=1)`
- Psalm runs at error level 1 with `findUnusedCode` enabled; suppress unused classes injected by Nextcloud with `@psalm-suppress UnusedClass`

### Frontend checks and `@nextcloud/vue` gotchas

`npm run typecheck` is the only check that sees third-party component prop types — ESLint cannot, because no rule reads `@nextcloud/vue`'s type definitions. CI runs it via `.github/workflows/lint-typescript.yml` (the org template, which calls `npm run ts:check`, the alias; it skips silently if that script is missing). **Run it after every `@nextcloud/vue` bump** — that is the class of breakage it exists to catch. It does **not** catch CSS or layout regressions; those need a look at the running app.

Breakages already hit, kept here so they are not reintroduced:

- **`NcButton` colour is `variant`, not `type`.** v9 removed the fallback: `type` is now the native HTML button type (`button`/`submit`/`reset`) and `variant` takes `primary` / `secondary` / `tertiary` / `tertiary-no-background` / …. The same applies to `NcActions` and `NcDialogButton`. `type="primary"` fails silently — the button renders in the default `secondary` variant and emits an invalid HTML `type` attribute.
- **`NcDateTimePickerNative` renders an `NcInputField` since 9.10**, whose root `.input-field` is `width: 100%`. As a flex child it claims the whole row, so the Journal's "Go to date" popover wraps the picker in a fixed-width `.datePicker` div (`JournalView.vue`). Putting a width class on the component itself does not work: `.input-field` is scoped with an attribute selector and outranks a plain class. `@nextcloud/vue` v9 ships no Tooltip directive, so icon buttons carry a native `title` with the same text as their `aria-label`.
- **`NcSelect` keeps a 260px minimum width** (`.nc-select.v-select.select`, 0,3,0), so it overflows a narrower column and doesn't follow a wider one. To size it, outrank that rule: `.myClass:global(.nc-select.v-select.select) { width: 100%; min-width: 0; max-width: none }` (as `ChoiceField.vue` and the Decimal places selects do), and set the width on its container. **Its list keeps vue-select's 160px minimum** (`--vs-dropdown-min-width`) too, which NcSelect never meets with its own 260px field: a narrower field gets a list wider than itself (NcSelect sizes the list to the field, then the minimum wins). The list is mounted on `<body>`, so `ChoiceField.vue` removes the minimum with a global rule on `.nc-select__dropdown.vs__dropdown-menu`; it reaches every list in the app but only changes one whose field is under 160px.
- **A plain `<input>` gets core's 2px border**, not `NcTextField`'s look. `NumberField.vue` copies `NcInputField`'s Nextcloud 32+ rules instead: `border: none`, a box-shadow ring (1px at rest, the text colour under the pointer, 2px with focus), so the text never moves.
- **`NcTextField` shows its label inside the empty field**, so a placeholder never shows: put "(optional)" in the label instead.
- **`NcTextArea` doesn't grow with its text**; `NoteField.vue` sets its height from `scrollHeight` on input. It passes `$attrs` (`maxlength`, `aria-label`, `readonly`) to the `<textarea>`.
- **Nextcloud's core CSS styles every native `<button>` that isn't an `NcButton`** (`core/css/inputs.css`: `button:not(.button-vue, [class^="vs__"])`) as a light primary button: tinted background, padding, 34px min-height, bold, a 3px margin. Its selectors are 0,1,1 (0,2,1 with `:hover`, `:focus`, `:disabled`, and for the margin), so a single CSS-module class loses silently. Plain buttons (grid headers, Journal cells, "Show more") are styled under their component's root class (`.grid .dateButton`, `.cell .noteButton`, `.note .more`), as a scoped style would be, reset `background` on `:hover`/`:focus` too, and take `margin: 0 !important`. `NcButton`s aren't affected; colour their icon (`NcIconSvgWrapper`) rather than the button, whose scoped tertiary colour outranks a class.
- **`NcCheckboxRadioSwitch` draws its state from `modelValue`**, so a refused write needs no putting back (unlike the native `input.checkbox` in Journal cells, which flips itself). To stop a click on it, catch it in the capture phase on a wrapper and `stopPropagation()`: its click handler sits on an inner element, not the input. (Locked days no longer need this: they render no control.)
- **Nextcloud's `input.checkbox + label::before` has an uneven margin** (3px before, 6px after), so a box meant to sit on a centre is off by 1.5px; `JournalCell.vue` zeroes it under `.cell .checkboxSlot`.
- **A CSS module renames every class in its selectors, core's too.** In a `<style module>`, `input.checkbox` compiles to `input._checkbox_x1y2z`, which matches nothing, silently: a class the module doesn't own (core's `checkbox`, vue-select's `vs__clear`, NcSelect's `nc-select`) must be written `:global(.checkbox)`. `JournalCell.vue`'s checkbox rules were written without it and never applied until 20 Nov.
- **A library component's scoped root rule is 0,2,0** (`.icon-vue[data-v-…]` on `NcIconSvgWrapper`, `.button-vue[data-v-…]` on `NcButton`), and its stylesheet tends to load after the app's, so two classes only tie and lose: use three (`.archivedItem .handleSpace.handleSpace`, `TracksView.vue`) to change its `display`.

## Known gaps / future work

Surfaced while writing the mobile companion app integration guide (`mobile_instructions.md`):

Counter increments merging across devices, once a gap here, are done: `POST /api/ticks/increment` (signed delta, flag `counterIncrement`). Note that a timestamp alone would never have fixed it: two devices pushing the same absolute value are both wrong, so last-write-wins just picks one.

- **No sync delta endpoint.** The API has no `modifiedAt`, ETag, or `since=` parameter. Clients (especially the Android app) must poll full ranges and reconcile locally. If mobile sync UX proves clunky, consider adding a lightweight "changed since X" endpoint. Note this needs **more than a `modified_at` column**: because storage is sparse (untoggling/zeroing deletes the row), a `since=` query over live rows would never surface deletions. A real fix needs tombstones (soft-delete + `deleted_at`) or a separate change log, plus the timestamp/version column. Notes have the same gap (no `modified_at`, deletions are deleted rows), so a delta endpoint must cover them too. Exposed via the `syncDelta` capability flag when it lands.
