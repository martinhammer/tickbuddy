# Backend

## Backend layers

Follows the Nextcloud AppFramework pattern: **Entity → Mapper → Service → Controller**.

- `lib/Db/` — Entities (`Track`, `Tick`, `Note`, `IdempotencyKey`) and QBMappers. All DB queries live here.
- `lib/Service/` — Business logic. `TrackService` enforces the 99-track limit, type validation, and name trimming. `TickService` handles toggle (boolean), set (counter value or yes/no state) and increment (counter). `StatsService` works out per-track stats and streaks. `NoteService` reads and writes notes and owns the note text rules (`normalise`), which `TickService` and `ImportService` reuse. `StrictHandling` reads `Prefer: handling=strict` (RFC 7240); every write refused on an archived track calls its `refuseArchived($track)`, which throws `ReadOnlyTrackException` (423) for a client that asked and returns for the rest. `ErrorReason` holds the `reason` values of error answers. `IdempotencyService` honours `Idempotency-Key` on the five writes that aren't safe to repeat (see Key design decisions below). `ImportService` handles Tickmate and JSON imports. `ExportService` handles JSON export. `PublicLinkService` manages public links and answers what a call needs (`findByToken`, `isLive`, `touch`, `todayFor`); `EditableDays` is the server's copy of `src/editableDays.ts` (its values, labels and `allows`), also behind `PreferencesController`'s list; `RequestBody` reads a POST's `text/plain` body (at most 64 KiB), which Nextcloud leaves unread.
- `lib/Controller/` — OCS API controllers. Routes are defined via PHP attributes (`#[ApiRoute]`), not in a routes file.
- `lib/Middleware/` — `PreferenceAppliedMiddleware`, registered in `Application::register()`: adds `Preference-Applied: handling=strict` to every OCS controller response for a request that sent it.
- `lib/Settings/` — `PersonalSection` (sidebar entry with icon) and `PersonalSettings` (renders the settings template).
- `lib/Dashboard/` — `WeekWidget`, the dashboard widget (see `.claude/rules/dashboard.md`).
- `lib/BackgroundJob/` — `PurgeIdempotencyKeys`, a daily `TimedJob` registered in `appinfo/info.xml` (`<background-jobs>`) that deletes `Idempotency-Key` rows older than `IdempotencyService::KEEP_DAYS` (30).
- `lib/Capabilities.php` — implements `OCP\Capabilities\ICapability`, registered in `Application::register()`. Advertises the app version and a feature-flag map to clients via the core capabilities endpoint (see `.claude/rules/api.md`). Keep `getCapabilities()` cheap (no DB) — it runs on every capabilities request.
- `lib/Migration/` — Database schema migrations.
- **App metadata**: `appinfo/info.xml` (Nextcloud app manifest — version, dependencies, navigation entry).
- **OpenAPI spec**: `openapi.json` is auto-generated from PHP docblocks on API controllers.

## Data model

Six tables, all scoped per-user:

- **`tickbuddy_tracks`**: id, user_id, name, type (`'boolean'` | `'counter'` | `'number'` | `'choice'`), sort_order, private (int 0/1, exposed as bool at the API), archived_at (nullable DATE, mapped as a `YYYY-MM-DD` string; null = active), and four nullable columns, null on every other type: a Number's unit (STRING 255, NULL when empty, as Oracle stores `''` as NULL; answered as `""`), decimal_places (SMALLINT 0–3) and allow_negative (INTEGER 0/1, as private), a Choice's ordered_scale (INTEGER 0/1). Max 99 tracks per user, archived ones included.
- **`tickbuddy_ticks`**: id, user_id, track_id, date, value (int, default 1): a Counter's count, 1 for Yes/No, a **Number's value in whole thousandths** (10.4 is 10400; the column stays INTEGER, so the limit is ±2,147,483.647, `NumberValue::MAX_MILLI`), a Choice's place (1 to n). Unique on (user_id, track_id, date).
- **`tickbuddy_track_options`**: id, user_id, track_id, place (SMALLINT, 1 to 99, the value a day stores), label (STRING 255). Unique on (track_id, place). A Choice's options, fixed once created: only labels change (`PUT /api/tracks/{id}/options/{value}`). Go with their track (delete) and with both Replace imports.
- **`tickbuddy_notes`**: id, user_id, track_id, date, text (TEXT; the 500-character limit, `NoteService::MAX_LENGTH`, lives in PHP so it can change without a migration). Unique on (user_id, track_id, date). Its own table, not a column on ticks, because ticks are sparse: unticking deletes the tick row, and a note must outlive that.
- **`tickbuddy_idempotency`**: id, user_id, idem_key (the lower-cased UUID), fingerprint (SHA-256 hex), status (nullable INTEGER; null while the first request runs), response (nullable TEXT, the answer's `ocs.data` as JSON), created_at (BIGINT, Unix seconds). Unique on (user_id, idem_key). Not user data: not exported, imported or deleted with tracks; purged after 30 days.
- **`tickbuddy_public_links`**: id, user_id (the owner), track_id, token (32 characters of `ISecureRandom::CHAR_HUMAN_READABLE`, unique, kept as it is so the link can be copied again), name, permission (`'tick'` | `'view'`), allowed_days (Editable days' values), last_used_at and revoked_at (nullable BIGINT, Unix seconds). **Revoking keeps the row** (Tickbuddy's only soft delete), so a call to a revoked link can be told from a guess: only a token that never existed counts towards brute-force protection, which would otherwise slow every link called from that server. Rows go with their track (delete), and with both Replace imports; archiving revokes them. Not exported or imported.

## Key design decisions

- **Sparse storage**: a tick row existing means "yes" / non-zero count. No row means "no" / zero. Toggling a boolean track inserts or deletes the row. Setting a counter to 0 deletes the row. **For Yes/No and Counter only**: a Number or Choice stores every value as an entry, a Number's 0 included, and no row means no value (`null` at the API, never 0). `TickService::writeValue` stores any int and deletes on null; the counter path passes `0` as null.
- **Number and Choice.** A Number is stored in thousandths (as Loop does, so a later Loop importer copies values across) and travels as a JSON number holding the stored value exactly (`NumberValue::toWire`: `10.45`, `-1.5`, `72` without `.0`; at most 10 significant digits, so a double holds it). The API answers the stored value, not one rounded to the track's current decimals: fewer decimals only show older days rounded, and switching negative values off keeps past negative days. Every write path (`set`, public links) **rounds to the track's decimal places, half away from zero**, on digit strings (`NumberValue::parse`, never a float; a JSON float is first written back with `json_encode`). This is the one place the server alters rather than refuses, because Decimal places can change later and a script sending two decimals must not start failing. `set` with `value` null or `""` clears a Number or Choice day, and **a `set` without `value` is 400** (the controller asks the request whether it holds `value`; the fingerprint holds `['missing']` then, a list no sent value can be); a public link's `value=` stays 400, so an empty reading can't wipe a day. `toggle` stays Yes/No only, `increment` Counter only. An unknown type in `set` is 400 `wrongTrackType`, never the counter branch. Settings of another type (`unit` on a Choice, `options` on a Number) are 400 on create, update and import. Option labels are trimmed, 1 to 255, and no two the same ignoring case (`mb_strtolower`), unlike track and link names, so a drop-down and a script picking by label can tell them apart. Create writes the track and its options in one transaction inside the end-of-list retry, a new entity each attempt.
- **`includeAllTypes`.** `GET /api/tracks`, `/api/ticks`, `/api/notes`, `/api/stats` and the reorder's answer list only `TrackService::BASE_TYPES` (Yes/No and Counter) unless the client sends `includeAllTypes=true` (read with `Flags`), so a client that predates a type never meets it (Tickcli decision 32, `notes/forward-compat.md`). `trackId` names its track whatever its type, as it names an archived one without `includeArchived`. Bounds, the export, the public link call and every write ignore it. Ticks and notes filter with an id list (`TrackMapper::findIdsByUserAndTypes`), not a join. The web sends it on every read (`api.ts` `ALL_TYPES`, and the reorder in `TracksView.vue`). A new type joins `VALID_TYPES` only, never `BASE_TYPES`, and gets a capability flag.
- **Track type is immutable**: set at creation, cannot be changed afterward. The API rejects updates to the `type` field.
- **JSON backups match ticks to tracks by `trackIndex`, else by unique name.** Track names may repeat, so `ExportService` adds `trackIndex` (position in the file's `tracks`) to ticks whose track name isn't unique in the file, and only then, so files without duplicates keep the original shape. `ImportService::resolveJsonTicks` resolves every tick to a position *before* the transaction: an invalid `trackIndex`, or a name-only tick matching several tracks, fails the import with nothing written. Tick names are cleaned like track names (trimmed, blank → "Untitled").
- **A Tickmate track is a counter if its "multiple entries per day" setting is on _or_ it has several ticks on one day.** Both checks are needed: older Tickmate backups lack the `multiple_entries_per_day` column, and a track switched off after counting still holds counts that a yes/no import would collapse. Don't simplify it to either check alone: track type is immutable, so a wrong guess can't be corrected after import.
- **Archive.** An archived track (`archived_at` set) keeps its ticks and its `sort_order`, but leaves `GET /api/tracks` unless `includeArchived=true`, and so leaves Today, the journal and the dashboard widget without any change to their code (Analytics asks for archived tracks only to show one opened from Tracks). An archived track can only be restored or deleted: every other change (ticks, notes, rename, private, `sortOrder`, re-archiving, a reorder that lists it) is refused with **423 Locked** `{message, reason: "archived"}` for clients that send `Prefer: handling=strict`, and quietly ignored for the rest; the server confirms the header with `Preference-Applied` (no capability flag: an older server just ignores it). Refused whatever the value, so a write that would change nothing gets 423 too. Two compatibility choices here look like bugs and are not — don't "fix" either into an error: (1) **hiding archived tracks by default** is what keeps clients that predate archiving (Tickdroid ≤ 1.2.0) working: the track just disappears for them; (2) **without `Prefer: handling=strict`, writes on an archived track answer 200 (204 for note delete) with the unchanged state** (after the usual 404 and 400 checks), because Tickdroid ≤ 1.3.0's upload queue retries forever on any error but 401 and one stale tick would stall it. This stays until the deprecation switch, when `refuseArchived` throws for every client and the legacy branches go. Restore moves the track to the end of the list (`getMaxSortOrder + 1`) and still applies a name or private sent with it; re-archiving keeps the first date. The archive date is the client's today (`archivedAt`), the server's date only as a fallback. Tick reads (`GET /api/ticks`, `/bounds`) still include archived tracks' ticks; clients match ticks to the tracks they list.
- **Notes outlive ticks, and empty text deletes everywhere.** A note can sit on a day without a tick; unticking (from any client) never touches it, and a note-only day is not a tick in `ticks`, `bounds` or `stats`. Text is stored as sent apart from `\r\n`/`\r` → `\n` and trimming; the server refuses (400, nothing written) rather than alters: not UTF-8, control characters other than `\n`/`\t`, over 500 code points. No HTML stripping or escaping on the way in: whoever displays a note escapes it (the web must use `{{ }}`, never `v-html`). Empty after trimming means "no note" in every write path (`notes/set`, `note` on tick calls, imports, which skip it); appending empty text changes nothing. Archived tracks' notes can't change: 423 for strict clients, the same quiet 200/204 as ticks for the rest. Track delete and both Replace imports delete notes.
- **`note` on `toggle`/`set`/`increment` is optional, and missing ≠ empty.** Missing (null) leaves the day's note alone; sent (even `''`) writes it, and only then does the answer carry `note`. All checks (track, type, value/delta, date, then the note) run before the tick write, then the note is written after it, without a transaction (as for increment). The controllers type `note`/`text` as a scalar union, not `string`: under `strict_types` Nextcloud passes a JSON number through uncast, and a `string` parameter would answer a bare 400 instead of storing the digits.
- **Appending to a note is a compare-and-swap, not a transaction.** `NoteService::appendForTick` reads the note, works out the result (skip if the text's lines already appear as consecutive whole lines, unless duplicates are allowed; 400 if over the limit), then writes it with `NoteMapper::replaceText` (`UPDATE … WHERE id = :id AND text = :old`), or inserts when there is no note. Losing either race (0 rows, or a unique violation) reads again, 3 attempts, then 409. No transaction for the same PostgreSQL reason as increment. The `text` comparison passes `PARAM_STR` explicitly so Oracle compares `to_char(text)`, as a CLOB can't be compared directly. On tick calls, `NoteService::checkAppend` checks the result's length before the tick is written; a 409 (or a note that grew past the limit in between) can only come after it.
- **Idempotency-Key on the writes that aren't safe to repeat, without a transaction.** `POST /api/tracks` (a retry makes two tracks), `toggle` (flips back), `increment` (counts twice), `notes/append` (with `allowDuplicate`, adds twice) and `set` (only unsafe with `appendNote` + `allowDuplicateNote`, but honoured on every `set` to keep the rule simple) take an optional `Idempotency-Key` (draft-ietf-httpapi-idempotency-key-header) holding a UUID, quoted or not (400 `invalidValue` otherwise). Every other write ignores it, as do imports. Each controller method passes its endpoint name and **every parameter in signature order** to `IdempotencyService::run`, which wraps the method's existing body unchanged: claim the key first in its own row (the unique index is the lock), run the body, store its status and data **whatever the status** (a 423 or 409 `noteConflict` replays too), and answer a repeat with the stored answer. A different fingerprint (other parameters, or another endpoint) is 422 `idempotencyKeyReused`; a claim with no answer yet is 409 `requestInProgress`, until it is 5 minutes old (`CLAIM_TIMEOUT_SECONDS`), when it is released (conditional `DELETE … WHERE status IS NULL AND created_at < :t`) and the repeat runs as new: a write may then happen twice, but only after a server failure inside that one request. Failing to store the answer still answers the client. Keys are kept 30 days. No transaction around the key and the write, for the same PostgreSQL reason as increment (a unique violation aborts the whole transaction, and the increment and note writes rely on catching them). The fingerprint is SHA-256 of `serialize()`, not JSON: it keeps `1`/`"1"`/`true`/`null`/`''` apart and can't fail on text that isn't UTF-8 (which a JSON fingerprint would). Changing the fingerprint's recipe answers 422 to in-flight retries for up to 30 days, so don't, without a reason. **Adding a parameter to one of the five changes its fingerprint the same way**: harmless only between releases. A new unsafe write needs a capability flag of its own before it honours the key.
- **Reorder always renumbers every track, in one transaction.** `TrackService::reorder` reads the user's tracks locked (`findAllByUser(…, true)`, `FOR UPDATE`), builds the full order (`fullOrder()`: listed ids first, then every other track in its previous order), and `TrackMapper::reorder` renumbers, so unlisted tracks (archived ones, or ones another device just created) never keep a placeholder and jump to the top. The renumbering first shifts every track below both 1 and its lowest value, then numbers them 1..n: MySQL and SQLite check the unique index row by row, so the old single negation (`-(sort_order + 1)`) failed on a mix of positive and negative values, and without a transaction a failure halfway left exactly that mix, which every later reorder then failed on. The shift repairs such an order too. A create or restore elsewhere (`max + 1`, not locked) can still take a number mid-reorder: the unique violation rolls the whole reorder back and it is retried, 3 attempts, then 409 `databaseConflict`. Catching the violation is safe inside this transaction, unlike increment's, because the retry starts a new one.
- **Three tick mutation endpoints**: `POST /api/ticks/toggle` (boolean tracks only), `POST /api/ticks/set` (both: a counter's absolute value, or a yes/no state) and `POST /api/ticks/increment` (counter tracks only). The service layer validates the track type matches the endpoint. All three check `date` is a real `YYYY-MM-DD` date (400, nothing saved). Checks run in the order `allowDuplicateNote` (400), track (404), type (400), value or delta (400), date (400), note (400), then the archived track's quiet 200, or 423 for strict clients. A counter's `value` and `delta` are whole numbers (`TickService::parseWholeNumber`: a JSON integer, or a trimmed string of digits, `delta` with an optional minus; not floats, booleans, `+5`, `5.0` or `5abc`), `value` from 0 (missing or negative is 400, 0 deletes); the limit is `TickService::MAX_VALUE`, 2147483647, the column's range: `set` above it is 400, an `increment` past it is 400 with nothing written (the bound is a condition of the atomic `UPDATE`, which `TickMapper::addToValue` takes as `$max`; a lost insert then reads the row to tell "too large" from "no row"), and a delta below −2147483647 counts as −2147483647, which empties any day.
- **Increment is atomic without a transaction.** `UPDATE … SET value = value + delta` first (the common case is an existing row); with no row, insert, and on a unique-constraint violation (another request inserted it meanwhile) retry the UPDATE; if that row is gone again by then (a decrement to 0, a `set` of 0), insert again, 3 attempts, then the database error (nothing stored: never an answer of 0 for a delta that wasn't applied). A transaction would break that retry on PostgreSQL, where a unique violation aborts the whole transaction. Results of 0 or less delete the row.
- **Losing an insert race is never a 500.** Every insert of a day's tick or note, and every move of a track to the end of the list, catches the unique violation and finishes against the row that won: `toggle` deletes it (two toggles from an unticked day end unticked), yes/no `set` is already as asked, counter `set` and note writes (`writeForTick`) replace its value (last write wins) or insert again if it is already gone, create and restore read the track limit and the end of the list (`getMaxSortOrder + 1`) again. 3 attempts, then the database error escapes, with nothing written. Keep these catches: an exception escaping the controller also leaves an `Idempotency-Key` claim unanswered, so the client's retries get 409 `requestInProgress` for 5 minutes. The 99-track limit is still a count before the insert, so two creates at the same moment can end at 100.
- **Stats.** The client sends `today`, because the streak rule depends on whether today is open (server date only as a fallback). Each track ends on its end day `E`: the earliest of `to`, `today` and an archived track's `archivedAt`, so an archived track reads as it stood that day. Future ticks (after `E`) are ignored everywhere. It starts on `S`: `from` when given (every day of the period takes part, so unticked days at its start are a break and a tickless period is one break), else the first tick. Only ticks from `S` to `E` count; runs crossing either edge are cut there, `current`/`upToYesterday` are as of `E`, and `E` before `S` gives the empty answer. The weekly mean runs from `S` to `E`, **counting both end days**, floored at one week, so ticking every day reads exactly 7. `StatsService` reads plain rows (`TickMapper::findValuesByUser`), not entities, and works on day numbers, so a DST change can never make a day 23 or 25 hours.
- **Track names are capped at 255 characters** (`TrackService::MAX_NAME_LENGTH`, the column size), checked in PHP because SQLite doesn't enforce it; imports refuse longer names before writing anything, and the web's name fields carry `maxlength`.
- **A NOT NULL column whose entity property starts with a value needs the same `default` in its migration** (why: nextcloud `php-backend` skill). `tickbuddy_tracks.type` has `'boolean'` for `Track::$type`, `tickbuddy_public_links.permission` `'tick'` and `allowed_days` `'activeAndPrevious'`. The unit tests mock the mappers, so none of them can see a missing default.
- **Stats on Number and Choice count days with an entry**: each stored day counts 1 in `total`, `weeklyMean`, `last7`, `previous7` and `peak7`, and is part of a streak (a Number's 0 and negative values too: `runsFromDays` works on keys). `maxValue`/`minValue` are the highest and lowest stored value over days with an entry (`summarise(…, $countsEntries)`), in the API's form, null without one, and **always null on a plain Choice list** (`orderedScale` off), whose places have no order. Both are `int|float|null` now. The web shades Number squares between them (`heatmap.ts` `trackLevel`).
- **`private` is stored as an integer, not a boolean.** The physical column is `INTEGER` on every database (`Types::BOOLEAN` failed to migrate on MySQL), so the `Track` entity must map it with `addType('private', 'integer')` (why it must match the column: nextcloud `php-backend` skill). `bool` exists only at the API/JSON boundary — the controller serializes `getPrivate() === 1` and services convert incoming bools with `? 1 : 0`. Golden rule: an entity's `addType()` must always match the physical column type.
- **A migration that has shipped in a tag is immutable.** Correct it with a *new* migration, never by editing it. `Version1001Date20260418000000` created `private` as `Types::BOOLEAN` and was edited to `Types::INTEGER` after v1.0.0 was tagged; because the step is wrapped in `hasColumn('private')`, the edit never reaches a database that already ran the old version — it stays a no-op there forever, and re-enabling the app does not reconcile it (the migration is already recorded as run). No users were affected: v1.0.0/v1.0.1 predate the app store listing (first store release was 1.0.2) and their GitHub assets had zero downloads, so only dev instances installed from source in that window kept the drifted column. Note the asymmetry if this ever recurs: `Types::BOOLEAN` renders as `tinyint(1)` on MySQL, which is harmless for a 0/1 flag, but as a *native* `boolean` on Postgres, where the integer entity reads `'t'`/`'f'` as `0` and integer writes are rejected outright — and converting that column back needs an explicit `USING private::int` cast, not a plain type change.
